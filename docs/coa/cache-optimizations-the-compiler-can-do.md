# Cache optimizations the compiler can do

Hardware caches operate automatically using fixed lookup and replacement policies, but their performance depends heavily on the memory access patterns generated by code emission. Compilers restructure access patterns and layout data to maximize spatial and temporal locality, directly reducing the cache miss rate component of Average Memory Access Time.

:::tip Read these first
- [/docs/coa/memory-hierarchy](/docs/coa/memory-hierarchy) — Memory hierarchy: locality and miss cost dominate compiler output
- [/docs/coa/cache-mapping](/docs/coa/cache-mapping) — Cache mapping: direct, set-associative, fully associative
:::

:::important What you should leave with
- The compiler controls instruction sequence and layout, which dictates memory addresses and striding; hardware controls cache line replacement and physical fetch timing.
- AMAT equals $\text\{Hit Time\} + (\text\{Miss Rate\} \times \text\{Miss Penalty\})$; compilers directly reduce Miss Rate through loop transformations and reduce perceived Miss Penalty through software prefetching.
- Loop tiling (blocking) trades loop overhead for temporal locality by keeping active data working sets inside a fixed cache level.
- Struct field reordering and alignment eliminate false sharing and spatial waste, guaranteeing every byte transferred in a cache line is utilized.
:::

:::caution Who this is not for
If you are looking for microarchitectural cache control mechanisms like way prediction, critical-word-first transfer, or physical cache replacement policies, see your processor's hardware reference manual. The compiler cannot directly alter internal cache hardware policies.
:::

:::note
Compilers can only optimize memory accesses that can be statically analyzed or bounded by runtime checks. Unsafe pointer arithmetic and opaque alias chains restrict automated cache transformations.
:::

## The AMAT Equation and Compiler Levers

Cache performance is evaluated using Average Memory Access Time (AMAT):

$$\text\{AMAT\} = \text\{Hit Time\} + (\text\{Miss Rate\} \times \text\{Miss Penalty\})$$

In the CPU performance equation ($\text\{CPU Time\} = \text\{Instruction Count\} \times \text\{CPI\} \times \text\{Cycle Time\}$), memory latency manifests as stall cycles that inflate the average Cycles Per Instruction (CPI). 

```
               +------------------------------------+
               |    Average Memory Access Time      |
               | (Hit Time + Miss Rate * Penalty)   |
               +-----------------+------------------+
                                 |
        +------------------------+------------------------+
        |                                                 |
        v                                                 v
+-------------------------------+             +-------------------------------+
|     Data Layout Levers        |             |  Loop Iteration Levers        |
|  - Structure Padding          |             |  - Loop Interchange           |
|  - Field Reordering           |             |  - Loop Tiling / Blocking     |
|  - Cache Line Alignment       |             |  - Loop Fusion & Fission      |
+---------------+---------------+             +---------------+---------------+
                |                                             |
                +-----------------------+---------------------+
                                        |
                                        v
                       +---------------------------------+
                       | Transformed Assembly Stream     |
                       |  - Unit-Stride Load / Stores    |
                       |  - Maximized Cache Line Usage   |
                       |  - Software Prefetch Hints      |
                       +---------------------------------+
```

The hardware sets the base **Hit Time** and hardware **Miss Penalty**. The compiler influences:
1. **Miss Rate**: By ordering operations so that memory accesses hit the same cache line repeatedly before eviction (temporal locality) or consume consecutive bytes within a loaded cache line (spatial locality).
2. **Effective Miss Penalty**: By issuing non-blocking software prefetch instructions ahead of execution to overlap memory fetch latency with independent computation.

## The Mechanism: Transforming Access Patterns and Data Layout

A compiler affects cache performance through two primary vectors: **Code Transformation** (changing when memory is accessed) and **Data Transformation** (changing where data resides in memory).

| Optimization Technique | Primary Target Mechanism | Hardware Effect | Compiler Requirement |
| :--- | :--- | :--- | :--- |
| **Loop Interchange** | Spatial Locality | Converts strided accesses to unit-stride (stride-1) accesses, matching line-fill size. | Legal only when iteration dependency vectors permit reordering. |
| **Loop Tiling (Blocking)** | Temporal Locality | Subdivides large iteration spaces so working sets fit entirely inside L1/L2 caches. | Loop bounds must be affine; array references must have static affine indices. |
| **Struct Reordering & Packing** | Spatial Locality | Eliminates padding gaps and groups frequently co-accessed fields into single lines. | ABI layout rules must allow field reordering (or explicit flag like `-fpack-struct`). |
| **Software Prefetching** | Overlapping Miss Penalty | Issues explicit prefetch hints into execution stream ahead of data consumption. | Accurate loop trip count or distance heuristic to prevent cache pollution. |
| **Array Alignment** | Cache Alignment | Aligns base address of vectors to 64-byte boundaries to avoid line-crossing loads. | Allocator cooperation or backend stack frame alignment enforcement. |

## Loop Transformations for Locality

Compilers apply affine transformations to nested loops to align memory accesses with hardware cache line granularity.

<Tabs>
<TabItem value="interchange" label="Loop Interchange" default>

When a multidimensional array is stored in row-major order, inner loop iterations accessing columns sequentially produce unit-stride memory reads. Accessing rows sequentially in the inner loop produces large memory strides, fetching a full cache line but consuming only a single element before the line is evicted.

```c
// Suboptimal: Column-major access on Row-Major Storage
// Memory Stride = N * sizeof(double)
for (int j = 0; j < N; j++) {
    for (int i = 0; i < N; i++) {
        A[i][j] = A[i][j] * 2.0;
    }
}

// Optimized: Interchange loops for Unit-Stride Access
// Memory Stride = 1 * sizeof(double)
for (int i = 0; i < N; i++) {
    for (int j = 0; j < N; j++) {
        A[i][j] = A[i][j] * 2.0;
    }
}
```

By swapping loop headers `i` and `j`, every 64-byte cache line loaded brings in 8 contiguous double-precision values that are consumed in consecutive inner-loop iterations.

</TabItem>
<TabItem value="fusion" label="Loop Fusion">

Loop Fusion merges two adjacent loops that iterate over the same index space into a single loop.

```c
// Unfused: Array A is traversed twice
// If N is large, A[i] is evicted from L1 before second loop starts
for (int i = 0; i < N; i++) {
    A[i] = B[i] + 1.0;
}
for (int i = 0; i < N; i++) {
    C[i] = A[i] * 2.0;
}

// Fused: Array A[i] is consumed immediately after write
// Hits directly in L1 cache
for (int i = 0; i < N; i++) {
    A[i] = B[i] + 1.0;
    C[i] = A[i] * 2.0;
}
```

Loop fusion converts spatial locality across distinct loop passes into immediate temporal locality within the CPU registers or L1 cache.

</TabItem>
<TabItem value="tiling" label="Loop Tiling (Blocking)">

When working sets exceed cache capacities, data loaded at the start of an iteration space is evicted before subsequent iterations re-reference it. Loop tiling breaks the iteration space into smaller chunks (blocks) that fit within target cache dimensions.

```c
// Standard Matrix Multiplication: Matrix B is re-read N times, causing L3/RAM misses
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        for (int k = 0; k < N; k++)
            C[i][j] += A[i][k] * B[k][j];

// Tiled Matrix Multiplication: Working set fits in L1/L2
for (int ii = 0; ii < N; ii += BLOCK)
    for (int kk = 0; kk < N; kk += BLOCK)
        for (int jj = 0; jj < N; jj += BLOCK)
            for (int i = ii; i < min(ii + BLOCK, N); i++)
                for (int k = kk; k < min(kk + BLOCK, N); k++)
                    for (int j = jj; j < min(jj + BLOCK, N); j++)
                        C[i][j] += A[i][k] * B[k][j];
```

</TabItem>
</Tabs>

:::tip Note
The compiler's polyhedral framework analyzes distance vectors to prove that reordering iteration steps will not violate data dependencies before performing interchange or tiling.
:::

## Data Structure Layout and Alignment

Cache lines move between hardware memory levels in fixed blocks (typically 64 bytes). If an 8-byte integer spans across a 64-byte line boundary, the core must issue two separate cache line requests to access a single value (a split cache access).

### Field Reordering and Padding

Compilers reorder structure fields or insert padding to align types to their natural byte boundaries and pack hot fields together.

```c
// Unoptimized Struct: 24 Bytes due to padding gaps
// Fields crossing cache boundaries randomly
struct LegacyNode {
    char   flag1;    // 1 byte
    // 7 bytes alignment padding
    double val1;     // 8 bytes
    char   flag2;    // 1 byte
    // 7 bytes alignment padding
};

// Field-Reordered Struct: 16 Bytes
struct OptimizedNode {
    double val1;     // 8 bytes
    char   flag1;    // 1 byte
    char   flag2;    // 1 byte
    char   pad[6];   // 6 bytes tail padding
};
```

By placing fields with similar alignment requirements together, the compiler reduces overall object size. Smaller structures fit more instances per cache line, increasing spatial locality during array traversals.

### Array of Structures (AoS) to Structure of Arrays (SoA)

When code traverses an array of structures but reads only a small subset of fields from each structure, the unread fields pollute the cache line with unused data.

```
Array of Structures (AoS): Bad Spatial Locality when reading only 'x'
[ x0 | y0 | z0 | w0 ] [ x1 | y1 | z1 | w1 ] [ x2 | y2 | z2 | w2 ]
  |                     |                     |
  +--- Cache Line 0 ----+--- Cache Line 1 ----+

Structure of Arrays (SoA): Perfect Spatial Locality for SIMD and scalar sweeps
x: [ x0 | x1 | x2 | x3 | x4 | x5 | x6 | x7 ]  <-- Loaded in 1 Cache Line
y: [ y0 | y1 | y2 | y3 | y4 | y5 | y6 | y7 ]
```

Compilers perform automatic SoA transformations during vectorization passes when safe, maximizing valid byte density per cache transfer.

## Software Prefetching and Non-Temporal Hinting

When memory access strides are predictable but non-unit (or when hardware prefetchers fail due to complex access streams), compilers insert explicit software prefetch instructions.

### Software Prefetching
Software prefetch instructions tell the memory controller to fetch a line into cache cycles before the actual load instruction executes.

$$\text\{Prefetch Distance\} = \left\lceil \frac\{\text\{Memory Latency Cycles\}\}\{\text\{Loop Body Execution Cycles\}\} \right\rceil$$

```assembly
; Loop body iterating over array with prefetch distance of 16 iterations
.Lloop:
    prefetchnta [rdi + rcx + 128] ; Fetch line 128 bytes ahead into non-temporal cache
    vmovups    ymm0, [rdi + rcx]  ; Load current working block
    vaddps     ymm0, ymm0, ymm1
    vmovups    [rsi + rcx], ymm0
    add        rcx, 32
    cmp        rcx, rdx
    jl         .Lloop
```

:::warning
Issuing software prefetch instructions too early causes line eviction before use; issuing them too late fails to hide memory latency. Prefetching also consumes execution bandwidth and instruction cache space.
:::

### Non-Temporal Stores
When writing a large array that will not be read again soon, standard store instructions generate a **Read-Only-For-Ownership (RFO)** request, pulling the destination cache line into L1 before overwriting it. 

The compiler can emit **non-temporal store instructions** (e.g., `movntdq` on x86) to bypass the cache hierarchy entirely and write directly to main memory via streaming write buffers. This prevents polluting the L1/L2 cache with data that lacks temporal locality.

## A Worked Example: Matrix Multiplication Tiling

Consider multiplying two square matrices $A \times B = C$ of size $1024 \times 1024$ double-precision floats ($8 \text\{ MB\}$ per matrix, exceeding typical L1 and L2 cache sizes).

```c
void matmul_untiled(const double *A, const double *B, double *C, int N) {
    for (int i = 0; i < N; i++) {
        for (int j = 0; j < N; j++) {
            double sum = 0.0;
            for (int k = 0; k < N; k++) {
                // A[i][k] has unit-stride access
                // B[k][j] has stride-N access (reads 8 bytes, fetches 64 bytes, discards 56 bytes)
                sum += A[i * N + k] * B[k * N + j];
            }
            C[i * N + j] = sum;
        }
    }
}
```

### Unoptimized Stalls Analysis
In `matmul_untiled`:
1. `B[k * N + j]` steps down rows for every step of `k`.
2. Array `B` access stride is $1024 \times 8 = 8192 \text\{ bytes\}$.
3. Every iteration of `k` misses the cache once `N` exceeds L1 capacity, causing continuous L1/L2 miss stalls.

### Tiled Assembly Output Walkthrough

The compiler transforms the iteration domain into $32 \times 32$ element blocks, so a sub-matrix of `B` fits inside L1 cache ($32 \times 32 \times 8 \text\{ bytes\} = 8 \text\{ KB\}$).

```assembly
; Loop transformation: Outer tile loops control block offsets (r8, r9, r10)
; Inner execution loop operates entirely inside cache-resident tile
.L_inner_k_loop:
    vmovsd      xmm0, [rsi + rbx]        ; Load B element from tiled block in L1
    vfmadd231sd xmm1, xmm2, [rax]        ; Multiply-add with A element
    add         rax, 8                   ; Step A by 1 double (unit-stride)
    add         rbx, rdi                 ; Step B by stride (points within hot L1 tile)
    dec         rcx
    jnz         .L_inner_k_loop
```

**Walkthrough:**
- **`vmovsd xmm0, [rsi + rbx]`**: Reads from matrix $B$. Because $B$ is partitioned into blocks small enough to fit within L1, `[rsi + rbx]` hits directly in L1 cache after the first block fetch pass.
- **`vfmadd231sd xmm1, xmm2, [rax]`**: Reads from matrix $A$ along row `i` with unit stride (`+8` bytes). All 8 double values per 64-byte line are consumed sequentially without cache evictions.
- **Result**: The inner loop executes without experiencing main memory latency stalls, dropping the total cache miss rate drastically.

## What the Compiler Can and Cannot Do

The compiler is constrained by static analysis capabilities and runtime information boundaries:

### What the Compiler CAN Do
- **Restructure Loop Iterations**: Swap loop orders (interchange), break loops into sub-blocks (tiling), combine loops (fusion), or split loops (fission).
- **Layout Data Structure Fields**: Change internal padding, reorder struct fields, and enforce structural alignments (e.g., 64-byte alignment on global/stack arrays).
- **Insert Prefetch Hints**: Place non-blocking memory prefetch instructions inside loops with predictable strides.
- **Emit Non-Temporal Direct Stores**: Bypass cache hierarchies when writing large streams of un-referenced output data.
- **Align Functions and Branch Targets**: Pad code blocks with `NOP`s so loop entry points align with 16-byte or 64-byte instruction fetch boundary lines.

### What the Compiler CANNOT Do
- **Change Physical Hardware Policies**: The compiler cannot force a specific cache line replacement policy (like LRU vs. Pseudo-Random).
- **Alter Dynamic Heap Allocation Alignment**: Unless overridden by runtime libraries or specialized intrinsic calls (e.g., `aligned_alloc`), standard heap allocations returned by opaque dynamic libraries cannot be statically aligned.
- **Predict Unbounded Pointer Aliasing**: If two pointers `a` and `b` might overlap in memory, the compiler cannot safely reorder loads and stores across them without generating runtime guard checks or requiring C99 `restrict` keywords.
- **Exceed Register Capacity**: Tiling or loop unrolling increases register pressure. If the compiler tiles too aggressively, it runs out of architectural registers and causes memory **register spilling**, which offsets the cache benefits.

## Common Misconceptions

### 1. "Software prefetching always speeds up memory-bound loops."
**Correction:** Software prefetches consume execution slots in the decoder and execution pipelines. If hardware prefetchers already detect unit strides effectively, adding software prefetch instructions increases instruction count and can cause L1 cache pollution, degrading performance.

### 2. "Loop unrolling alone improves cache performance."
**Correction:** Loop unrolling decreases loop control overhead and increases instruction-level parallelism (ILP), but it does not change the memory access footprint or cache miss rate. Without loop interchange or tiling, unrolled loops encounter the same number of cache misses.

### 3. "Compilers can automatically reorder fields in all standard struct declarations."
**Correction:** Standard C and C++ language specifications require compilers to maintain field ordering in memory as declared by the programmer. Compilers can only reorder struct fields under specific flags (e.g., dead-field elimination or whole-program optimization passes) or in languages where ABI structure layout guarantees are explicit.
