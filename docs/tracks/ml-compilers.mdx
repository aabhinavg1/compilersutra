  <section className={styles.section} id="project">
    <div className={styles.sectionHead}>
      <span className={styles.sectionStep}>The project</span>
      <h2 className={styles.sectionTitle}>From market data to a compiled ML program</h2>
    </div>
    <h3 className={styles.subTitle}>The problem we want to solve</h3>
    <p className={styles.sectionDesc}>
      A trading desk receives new market data for stocks such as Reliance, TCS, and Infosys.
      Every few minutes it has to read the changing market and calculate a score. A later
      system may use that score. The score itself is the return over the next fixed window,
      such as the next five minutes.
    </p>
    <p className={styles.sectionDesc}>
      A simple program can check whether the price is above a line, or whether volume has
      increased. Add more inputs, and the relationships among them, and the rule list becomes
      hard to maintain. It also misses patterns that are present in past examples.
    </p>
    <p className={styles.sectionDesc}>
      The inputs are only bars that have already closed: recent returns, volume changes, and
      volatility. The future return is the label. It is not one of the inputs. If a future
      number leaks into the window, the network looks right and the problem is wrong.
    </p>
    <p className={styles.sectionDesc}>
      <strong>
        The challenge is to train a small model on those past examples, then run that frozen
        model efficiently on real hardware.
      </strong>
    </p>
    <ul className={styles.practiceList}>
      <li>Correctness. Does the compiled program produce scores close to the original PyTorch model?</li>
      <li>Performance. Do fusion, kernel choice, or a library call reduce latency or raise throughput? We measure this. We do not assume it.</li>
      <li>Hardware. How does the same model behave on a CPU and on a GPU, and what trade-off shows up in the measurement?</li>
    </ul>
    <h3 className={styles.subTitle}>What we will build</h3>
    <p className={styles.sectionDesc}>
      First, define the features and the target, prepare the historical examples, and train a
      small network in PyTorch. Inspect the learned weights, freeze the model, and keep that
      PyTorch run as the reference score.
    </p>
    <p className={styles.sectionDesc}>
      Next, export the model and read its computation graph. Follow that graph through an ML
      compiler: the intermediate forms, the optimizations, the lowering, the kernel or library
      that gets chosen, and the code for the target.
    </p>
    <p className={styles.sectionDesc}>
      Finally, run the compiled model on a CPU or a GPU. Compare its scores with the reference.
      Then measure latency for one input, and throughput for a batch, under conditions you write down.
    </p>
    <h3 className={styles.subTitle}>What we aim to achieve</h3>
    <p className={styles.sectionDesc}>
      By the end there is a path you can repeat: historical data, a trained model, a compiled
      program. You can point at where each transformation happens, check that the score still
      agrees, and use the benchmark to decide whether the compiled program is actually faster.
    </p>
    <p className={styles.sectionDesc}>
      <strong>The ML compiler is the engineering focus.</strong> It turns the frozen
      computation into a program for the target hardware. It does not train the model, decide
      that a trade is profitable, or place an order. The trading policy stays outside the project.
    </p>
