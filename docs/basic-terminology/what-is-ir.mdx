# What Is Intermediate Representation (IR)?

**Intermediate representation (IR)** is the compiler’s internal form of your program — after source has been understood, before (or while) machine code for a specific CPU is produced. Most modern optimization happens on IR, not on the original C/C++ text.

Reading time: about 8–10 minutes.

:::info Quick answer
**IR** = a structured, usually language-independent program form the compiler builds so it can analyze and transform code once, then generate machine code for many targets.
:::

## Why IR exists

A compiler could try to go straight from source characters to x86-64 instructions. That does not scale.

- Frontends for C, C++, Rust, and others would each reinvent optimization.
- Supporting a new CPU would mean rewriting every language frontend.
- Analysis (types, control flow, aliasing) needs a clean structure, not raw text.

So real compilers use stages:

```text
Source
  -> Frontend (lex, parse, semantics)
  -> IR
  -> Optimize IR
  -> Backend (select instructions, allocate registers)
  -> Assembly / object / machine code
```

## What IR is (and is not)

| IR is | IR is not |
| :--- | :--- |
| A program form the **compiler** uses internally | The same thing as your `.c` / `.cpp` file |
| Often designed for analysis and transforms | Always the same spelling across all compilers |
| Sometimes written to disk (`.ll`, bitcode, GIMPLE dumps) | Always human-friendly |

Examples of IR families (different projects, different designs):

- **LLVM IR** — used by Clang and many other frontends that target LLVM
- **GCC GIMPLE / RTL** — GCC’s pipeline forms
- **Bytecode** (JVM, some VMs) — a related idea: portable instructions for a runtime (may still be JIT’d later)

When people on CompilerSutra say “look at the IR,” they usually mean **LLVM IR** from Clang (`clang -emit-llvm -S`), unless they say otherwise.

## Tiny mental model

```c
int add(int a, int b) {
  return a + b;
}
```

You think in C. The compiler’s IR thinks in typed operations roughly like: “add these two integers and return.” Later, the backend turns that into real ISA instructions (`add`, `lea`, …) for your triple.

Exact IR text depends on the compiler version and flags. Do not memorize one dump as universal truth — verify with your installed toolchain.

## How to see LLVM IR (verified workflow)

On a machine with Clang:

```bash
clang --version
clang -O0 -emit-llvm -S add.c -o add.ll
```

- `-emit-llvm` asks for LLVM IR instead of normal object/asm output
- `-S` emits text (`.ll`) rather than bitcode alone
- Open `add.ll` in an editor — that file is IR, not the final binary

If Clang is missing, install a toolchain first; do not invent sample IR dumps from memory for publication.

## Common beginner mistakes

- Calling LLVM “a language you write apps in.” **LLVM** is infrastructure; **Clang** is a C/C++ frontend that lowers to LLVM IR.
- Thinking IR is always slower or always faster. IR is a *stage*; performance comes from later codegen and optimization choices.
- Confusing IR with assembly. Assembly is already close to one ISA; IR is usually still target-flexible.
