# What Is LLVM?

**LLVM** is a **compiler infrastructure**: a shared intermediate representation (LLVM IR), a library of analysis and transform passes, and backends that turn that IR into machine code for many CPUs. You usually meet it through **Clang**, a C/C++ frontend that lowers your source into LLVM IR and then uses the rest of the LLVM stack.

This Basic Terminology page is the **short, hands-on entry**. You will emit real LLVM IR, compare `-O0` vs `-O1`, run `llc` to assembly, and see why Clang ≠ LLVM. For the full architecture story (history, design rationale, deeper examples), use the existing longform article — do not treat this page as a second copy of it:

:::info Quick answer
**LLVM** = reusable compiler toolkit (IR + passes + backends). **Clang** = C/C++ (and related) frontend that targets LLVM. **LLVM IR** = the common program form those pieces share. LLVM is **not** “a language you write apps in.”

## A. Concept — What is LLVM?

### Simple definition

LLVM is a set of libraries and tools for building compilers. Frontends (like Clang) translate languages into **LLVM IR**. Middle-end passes analyze and transform that IR. Backends select instructions and emit assembly or object code for a target.

### Precise definition

In practice, “LLVM” refers to:

| Piece | Role |
| :--- | :--- |
| **LLVM IR** | Typed SSA-friendly intermediate language (text `.ll` or bitcode `.bc`) |
| **Pass pipeline** | Analyses and transforms (`opt`, and passes inside Clang/`llc`) |
| **Codegen / backends** | Lower IR toward a machine (`llc`, target libraries) |
| **Tooling** | Disassemblers, linker helpers, sanitizers, JIT APIs, and more |

**Name note:** LLVM originally stood for *Low-Level Virtual Machine*. Today it is treated as a proper name for the whole infrastructure — not a traditional VM you “install and run apps on.” Details and history live in [LLVM Explained](/docs/llvm/llvm_basic/intro-to-llvm/).

Official overview: [The LLVM Compiler Infrastructure](https://llvm.org/).

### Why it exists

| Problem | How LLVM helps |
| :--- | :--- |
| Every language reinventing optimizers | Share one IR + pass library |
| New CPU support per language | Add/maintain a backend once for many frontends |
| Hard to inspect “what the compiler sees” | Dump LLVM IR and run passes yourself |
| Research / tooling need a stable mid-level form | IR is a common engineering surface |

For “why LLVM won” and architecture depth, prefer the existing pages: [Why LLVM?](/docs/llvm/llvm_basic/Why_LLVM/) · [High-Level LLVM Architecture](/docs/llvm/llvm_basic/LLVM_Architecture/) · [LLVM Explained](/docs/llvm/llvm_basic/intro-to-llvm/).

## B. Mental model

```text
  Your .c / .cpp                 Clang frontend
  --------------                 --------------
  source text      ---------->   AST + semantics
                                        |
                                        v
                                   LLVM IR  (.ll / .bc)
                                        |
                    +-------------------+-------------------+
                    |                   |                   |
                    v                   v                   v
                 opt / passes      Clang -O*            llc / codegen
                 (transform IR)    (same stack)         (machine asm/obj)
                                        |
                                        v
                              object file → linker → executable
```

Analogy (limited): LLVM is a shared factory floor. Clang is one loading dock that accepts C/C++. The factory’s common product is LLVM IR; shipping is target codegen. Do not stretch the analogy — IR has precise types and rules, not “factory vibes.”

## C. Where LLVM fits

On CompilerSutra’s Basic Terminology track:

```text
Program → Source → Compiler
  → Lexer / Parser → AST
  → IR  (general idea)
  → LLVM  (the infrastructure + LLVM IR you will actually dump)
  → Machine code / object → Linker → Loader → Process
```

| Neighbor | Relationship |
| :--- | :--- |
| [Compiler](/docs/basic-terminology/what-is-a-compiler/) | LLVM is infrastructure many compilers use |
| [AST](/docs/basic-terminology/what-is-an-ast/) | Clang’s AST is before / around IR generation |
| [IR](/docs/basic-terminology/what-is-ir/) | LLVM IR is one concrete IR family |
| Machine code | Produced later by backends / assemblers |

## E. Actual output — emit LLVM IR

```bash
clang -S -emit-llvm -O0 add.c -o add.ll
cat add.ll
```

Verified excerpt (`-O0`, Clang 18.1.3, `x86_64-pc-linux-gnu`):

```llvm
; ModuleID = 'add.c'
source_filename = "add.c"
target datalayout = "e-m:e-p270:32:32-p271:32:32-p272:64:64-i64:64-i128:128-f80:128-n8:16:32:64-S128"
target triple = "x86_64-pc-linux-gnu"

; Function Attrs: noinline nounwind optnone uwtable
define dso_local i32 @add(i32 noundef %0, i32 noundef %1) #0 {
  %3 = alloca i32, align 4
  %4 = alloca i32, align 4
  store i32 %0, ptr %3, align 4
  store i32 %1, ptr %4, align 4
  %5 = load i32, ptr %3, align 4
  %6 = load i32, ptr %4, align 4
  %7 = add nsw i32 %5, %6
  ret i32 %7
}
```

Bitcode form (same IR, binary container):

```bash
clang -emit-llvm -c -O0 add.c -o add.bc
file add.bc
llvm-dis add.bc -o add.frombc.ll
```

Verified `file` line:

```text
add.bc: LLVM IR bitcode
```

## F. Line-by-line — reading the `@add` body

| Fragment | Meaning |
| :--- | :--- |
| `target triple = "x86_64-pc-linux-gnu"` | Default codegen target for this build of Clang |
| `define … i32 @add(i32 …, i32 …)` | Function returning `i32` with two `i32` args |
| `alloca` / `store` / `load` | `-O0` keeps parameters in stack slots |
| `add nsw i32` | Integer add; `nsw` = “no signed wrap” assumption metadata for optimizers |
| `ret i32` | Return the sum |
| `optnone` in attributes | At `-O0`, Clang often marks functions so many mid-level opts will not rewrite them |

At `-O0` you are seeing a faithful, almost “literal” lowering — great for learning, not the final optimized shape.

## G. Internal working — Clang + LLVM stack (beginner view)

1. **Frontend (Clang):** lex, parse, semantic analysis → AST, then **IR generation** into an LLVM module.
2. **Middle end:** pass managers run analyses/transforms on the module (in-process in Clang, or via `opt` on a `.ll`/`.bc` file).
3. **Backend:** instruction selection, register allocation, emission → assembly / object.

You do not need every pass name on day one. You do need this split: **language frontend** vs **shared IR/opt/codegen**.

## H. Practical experiments

### Experiment 1 — `-O0` vs `-O1` IR

```bash
clang -S -emit-llvm -O0 add.c -o add.O0.ll
clang -S -emit-llvm -O1 add.c -o add.O1.ll
diff -u add.O0.ll add.O1.ll | head
cat add.O1.ll
```

Verified `-O1` function body on this machine:

```llvm
define dso_local i32 @add(i32 noundef %0, i32 noundef %1) local_unnamed_addr #0 {
  %3 = add nsw i32 %1, %0
  ret i32 %3
}
```

**Observe:** stack `alloca`/`load`/`store` noise is gone; the add is direct. Same source, different IR after optimization.

### Experiment 2 — IR → assembly with `llc`

```bash
clang -S -emit-llvm -O0 add.c -o add.ll
llc add.ll -o add.s
head -n 35 add.s
```

Verified asm excerpt (x86-64):

```asm
add:                                    # @add
	.cfi_startproc
# %bb.0:
	pushq	%rbp
	movq	%rsp, %rbp
	movl	%edi, -8(%rbp)
	movl	%esi, -4(%rbp)
	movl	-8(%rbp), %eax
	addl	-4(%rbp), %eax
	popq	%rbp
	retq
```

**Observe:** LLVM IR `i32` args become ABI registers (`%edi`, `%esi` on this SysV x86-64 path) and a machine `addl`.

### Experiment 3 — Why naive `opt -passes=mem2reg` may no-op at `-O0`

```bash
clang -S -emit-llvm -O0 add.c -o add.ll
opt -S -passes=mem2reg add.ll -o add.mem2reg.ll
# Often unchanged while `optnone` is present on the function
```

Verified: with Clang 18 `-O0` IR, `mem2reg` left the alloca form in place because of `optnone`. Compare instead with `-O1` emit (Experiment 1), or strip `optnone` only as a learning hack — do not treat that hack as a production workflow.

## J. Common misconceptions

| Misconception | Correction |
| :--- | :--- |
| “LLVM is a programming language.” | LLVM IR is an **intermediate** form. Apps are written in C++, Rust, etc. |
| “Clang and LLVM are the same binary.” | **Clang** is a frontend (+ driver). **LLVM** is the broader infrastructure. |
| “LLVM IR is the CPU’s language.” | CPUs execute **machine code**. IR is still compiler-internal (until lowered). |
| “One IR dump is universal.” | Version, triple, and `-O*` change the text. Always re-run. |
| “GCC uses LLVM IR.” | GCC has its own forms (e.g. GIMPLE/RTL). Do not mix pipelines. |

## K. Knowledge check

**Conceptual:** Is LLVM primarily a language, an OS, or compiler infrastructure?

<details>
<summary>Answer</summary>
Compiler infrastructure (IR, passes, backends, tools).
</details>

**Practical:** Which flags emit textual LLVM IR from Clang?

<details>
<summary>Answer</summary>
`-S -emit-llvm` (plus your usual input file and `-o`).
</details>

**Reasoning:** Why share one IR across languages?

<details>
<summary>Answer</summary>
So optimizers and backends can be reused instead of rewritten per language.
</details>

**Application:** You have `add.ll`. Name one tool that can lower it toward assembly.

<details>
<summary>Answer</summary>
`llc` (or Clang’s own codegen path when compiling normally).
</details>
