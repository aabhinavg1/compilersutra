# What Is a Compiler?

A compiler is a program that translates source code written in a programming language into another form the machine can use — often machine code, assembly, or an intermediate representation. You write C, C++, Rust, or another language; the compiler turns that text into something a CPU (and the operating system) can actually run.

Reading time: about 8–10 minutes.

:::info Quick answer
A **compiler** translates a whole program (or translation unit) ahead of time into another representation. An **interpreter** executes the program more directly, usually without producing a standalone binary first.
:::

## Start with the problem

Humans like readable names, functions, and loops. CPUs understand opcodes and registers.

Someone has to bridge that gap. That bridge is the compiler (sometimes with an assembler and linker beside it).

Without a compiler (or an interpreter), your source file is just text. It does not run.

## The basic chain

```text
Idea
-> Source code (what you write)
-> Compiler (translation)
-> Object / IR / machine code
-> Linker (combine pieces)
-> Executable
-> Loader + CPU (run)
```

You do not need every stage memorized on day one. You do need the shape: **write → translate → run**.

## What a compiler actually does

At a high level, a compiler:

1. **Reads** your source code
2. **Checks** that it follows the language rules (syntax and many semantic rules)
3. **Analyzes** the program (types, control flow, data flow — depth varies by language)
4. **Transforms** it into a lower-level form
5. **Emits** output: object files, bitcode, assembly, or an executable (toolchains differ)

Modern compilers also optimize. Optimization means transforming the program so it should behave the same but run faster or use less memory — within the language rules.

## Compiler vs interpreter

| | Compiler | Interpreter |
| --- | --- | --- |
| When translation happens | Ahead of time (before run, or as a build step) | During execution (or via a short-lived compile) |
| Typical output | Binary, object file, or IR artifact | Immediate execution of the program |
| Examples people meet | `clang`, `gcc`, `rustc` | Classic Python / Ruby loops (engines vary) |
| Mental model | Build, then run | Run the source (or bytecode) directly |

Real systems blur the line. Java and C# compile to bytecode, then a VM may JIT-compile hot code. JavaScript engines parse, interpret, and optimize. For beginners, keep the distinction: **compile-ahead vs execute-through-a-runtime**.

## A tiny example (mental model)

```c
int add(int a, int b) {
  return a + b;
}
```

You see a function. The compiler eventually turns that into instructions like “add these two registers and return.” The exact instructions depend on the **ISA** (x86-64, AArch64, …) and on optimization settings.

## Common beginner mistakes

- Thinking the compiler “is the language.” The language is the rules; the compiler is one implementation of those rules.
- Ignoring warnings. Warnings are the compiler telling you something suspicious before the CPU finds it the hard way.
- Skipping the linker. Many “compile errors” are really link errors (`undefined reference`).
- Treating optimization as magic. Optimizers are aggressive but still bound by language semantics.
