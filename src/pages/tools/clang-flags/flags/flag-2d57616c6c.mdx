## What this flag actually does

-Wall enables a curated Clang warning group. The name is historical: it is not every diagnostic. Warnings are diagnostics, not proofs that a program is invalid, and the group’s membership can change between compiler versions.

## Why use it / when not to use it

Use it when the diagnostics / warnings behavior matches the build contract. Do not enable it selectively across mutually dependent translation units when it changes preprocessing, language rules, ABI expectations, or runtime instrumentation. Verify the effect with the exact compiler and target used by CI.

:::caution
This option does not repair invalid source, undefined behavior, data races, or an inconsistent build contract. It only changes the compiler mechanism described above.
:::

## Performance impact

This option is not a runtime optimizer. It does not change generated code by itself the way `-O2` or `-fvectorize` does. If a macro, include path, language mode, or warning set changes which code you build, measure **that program** with [CompilerSutraPerf](/docs/project/compilersutra-perf/) (`csperf run` / `csperf diff`) the same as any other code change. Do not treat frontend flags as free speedups.

## How it works inside Clang

### Implementation

| Stage | Source and implementation | What happens |
| --- | --- | --- |
| Options.td | [Options.td](https://github.com/llvm/llvm-project/blob/main/clang/include/clang/Options/Options.td) | Declares the warning-group option and its diagnostic-group membership. |
| Driver parsing | [Clang.cpp](https://github.com/llvm/llvm-project/blob/main/clang/lib/Driver/ToolChains/Clang.cpp) | The driver resolves the warning option group and forwards warning enable/disable arguments to `cc1`. |
| Invocation setup | [CompilerInvocation.cpp](https://github.com/llvm/llvm-project/blob/main/clang/lib/Frontend/CompilerInvocation.cpp) | Diagnostic option marshalling populates `DiagnosticsEngine` configuration; the group is not an optimization pipeline. |
| Frontend diagnostics | [DiagnosticsReference](https://clang.llvm.org/docs/DiagnosticsReference.html) | Sema, SemaExpr, parser, and frontend checks emit diagnostics belonging to the enabled group. |
| LLVM / backend | [Clang diagnostic architecture](https://clang.llvm.org/docs/DiagnosticsReference.html) | Warnings normally end before LLVM IR generation; they do not directly change backend lowering unless the build promotes them to errors. |
| Linker | [Clang stage selection](https://clang.llvm.org/docs/CommandGuide/clang.html#stage-selection-options) | The linker does not interpret `-Wall`; compile-time diagnostics must be handled before linking. |

~~~mermaid
flowchart LR
 A["-Wall"] --> B["Options.td"] --> C["Clang driver"] --> D["CompilerInvocation"] --> E["frontend / CodeGenOptions"] --> F["LLVM IR or diagnostics"] --> G["backend / linker"]
~~~

The -Wall spelling is handled by the driver and translated into frontend, diagnostic, target, IR, or runtime state as shown above. LLVM and the linker consume the resulting representation; they do not generally parse the original user-facing spelling.
