## What this flag actually does

`-fstack-protector-strong` instructs the compiler to insert a stack canary (guard variable) into frame layouts for functions matching specific vulnerability criteria.

Compared to `-fstack-protector` (which only triggers on character arrays larger than 8 bytes by default) and `-fstack-protector-all` (which instruments *every* function regardless of structure), `-fstack-protector-strong` strikes a balance between security coverage and performance.

### The "Strong" Heuristic Criteria

A function receives stack canary protection if it satisfies **any** of the following conditions:

1. **Array declarations of any size and type**: Declaring `char buf[4]`, `int arr[1]`, or a struct containing an array member. (Unlike `-fstack-protector`, size does not matter and type is not limited to `char`).
2. **Dynamic stack allocations**: Any call to `alloca()` or allocation of variable-length arrays (VLAs).
3. **Address-of local variables**: Taking the address of a local variable (e.g., `&local_var`) where the pointer could escape or be passed to another function.
4. **References to stack-allocated variables**: Passing a local variable by non-const reference or binding local references.

### Pipeline Lowering Steps

1. **Driver**: Maps `-fstack-protector-strong` to `-stack-protector 2` when invoking `clang -cc1`.
2. **Frontend (`clang::CodeGen`)**: Emits the function attribute `sspstrong` on LLVM IR `Function` definitions.
3. **LLVM Target-Independent CodeGen (`StackProtector` pass)**:
   - Scans the function IR. If `sspstrong` is present, it runs the `sspstrong` heuristic analyzer.
   - If triggered, it marks the frame to require stack protection.
   - Rearranges local variables so arrays/vulnerable buffers are positioned adjacent to the guard frame index.
4. **Target Backend (`PrologueEpilogueInserter` / SelectionDAG / GlobalISel)**:
   - Inserts the prologue instruction to load the guard constant (from thread local storage like `%fs:0x28` on Linux x86_64, or `__stack_chk_guard`) and store it onto the stack.
   - Inserts the epilogue instruction to reload the stack guard, compare it against the global/TLS reference, and branch to `__stack_chk_fail` on mismatch.

### Frontend IR Lowering Difference

Without stack protection:
```llvm
define void @_Z7processv() {
  %1 = alloca i32, align 4
  call void @_Z10fill_valuePi(ptr noundef %1)
  ret void
}
```

With `-fstack-protector-strong`:
```llvm
define void @_Z7processv() #0 {
  %1 = alloca i32, align 4
  call void @_Z10fill_valuePi(ptr noundef %1)
  ret void
}

attributes #0 = { sspstrong }
```

The presence of `sspstrong` signals the backend `StackProtector` pass to insert stack layout protections during Frame Lowering.

## Before vs. after assembly

Compiling for `x86_64-unknown-linux-gnu` with `-O2`:

<AsmDiff
  before={`# clang -O2 (Default / -fno-stack-protector)
process():
        sub     rsp, 8
        mov     rdi, rsp
        call    fill_value(int*)@PLT
        add     rsp, 8
        ret`}
  after={`# clang -O2 -fstack-protector-strong
process():
        sub     rsp, 24
        mov     rax, qword ptr fs:[40]   # Read stack guard from TLS
        mov     qword ptr [rsp + 8], rax # Place guard on stack
        mov     rdi, rsp
        call    fill_value(int*)@PLT
        mov     rax, qword ptr fs:[40]   # Read reference guard
        cmp     rax, qword ptr [rsp + 8] # Validate guard
        jne     .LBB0_2                  # Fail path on corruption
        add     rsp, 24
        ret
.LBB0_2:
        call    __stack_chk_fail@PLT     # Abort execution`}
/>

:::note Stack Frame Layout
Notice that the stack allocation size grew from 8 to 24 bytes to account for alignment and the 8-byte stack canary slot placed above the local storage.
:::

## Why use it / when not to use it

### Why use it
* **Production Security Standard**: Linux distributions (Fedora, Debian, Ubuntu, RHEL) compile packages with `-fstack-protector-strong` by default. It provides near-complete protection against stack buffer overflows with negligible runtime cost.
* **Smarter than `-fstack-protector`**: Standard `-fstack-protector` ignores non-char arrays (e.g. `int buf[2]`) and small buffers (`char buf[4]`), leaving obvious attack surfaces exposed.
* **Cheaper than `-fstack-protector-all`**: Avoids cluttering simple leaf functions, getters/setters, or pure mathematical functions with canary setups and teardowns.

### When not to use it
* **Bare-metal / OS Kernels without Runtime Support**: If your environment does not implement `__stack_chk_guard` / TLS stack guards or `__stack_chk_fail()`, compilation/linking will fail unless custom CRT support is provided.
* **Hard Real-Time Systems**: The extra conditional branch in the epilogue and potential catastrophic abort via `__stack_chk_fail` might be undesirable in mission-critical deterministic loops.
* **Extremely Tight Micro-benchmarks**: In small compute-bound inner loops operating on stack pointers, canary loading can pollute register pressure or memory bandwidth.

---

## Performance impact

Qualitatively, `-fstack-protector-strong` incurs minimal overhead across real-world workloads:

1. **Instruction Overhead**: Adds 2 memory reads (TLS load), 1 memory write (canary store), 1 comparison, and 1 conditional branch per matching function invocation.
2. **Stack Footprint**: Expands function frame size by at least 8 bytes (x86_64/AArch64) to hold the canary value, plus potential alignment padding.
3. **Cache / Register Pressure**: Spills 1 register (e.g., `rax` on x86_64) during epilogue checking.
4. **Branch Prediction**: The check branch (`jne .LBB0_2`) is heavily biased towards non-taken; modern branch predictors execute this with zero misprediction penalty in non-exploit execution paths.

## Adjacent options

* `-fstack-protector`: Enables canary insertion only for functions with character array buffers $\ge 8$ bytes (or custom `--param ssp-buffer-size`).
* `-fstack-protector-all`: Enables canary insertion for **all** functions regardless of contents.
* `-fno-stack-protector`: Explicitly disables all stack canary generation.
* `-fstack-clash-protection`: Protects against stack-clash attacks by emitting probe instructions on large dynamic stack allocations (`alloca` / large frames).
* `-fsanitize=safe-stack`: Clang/LLVM SafeStack pass that splits the stack into a safe stack (returns, non-escaped locals) and an unsafe stack (buffers, escaped locals).
