| Field | Details |

| **Flag** | `-emit-llvm` |
| **Type** | Action / Output Selector |
| **Default** | Off (Clang defaults to generating target machine code) |
| **Driver Pass-Through** | Forwards `-emit-llvm` to `-cc1` |
| **Optimization Sensitivity** | **O-level sensitive for IR content**: `-emit-llvm` emits IR after frontend optimization passes for the specified `-O*` level. |

## What this flag actually does

The `-emit-llvm` flag alters Clang's output generation stage. Instead of invoking the LLVM target backend to lower intermediate representation into target-specific assembly (`.s`) or ELF/COFF/Mach-O machine code (`.o`), Clang halts compilation at the LLVM IR stage and writes out the IR.

The actual format of the output depends on whether it is paired with `-S` or `-c`:
* `clang -S -emit-llvm file.c -o file.ll`: Emits human-readable LLVM IR text (`.ll`).
* `clang -c -emit-llvm file.c -o file.bc`: Emits binary LLVM bitcode (`.bc`).
* `clang -emit-llvm file.c`: Defaulting without `-c` or `-S` generates binary bitcode (`.bc`).

Because `-emit-llvm` intercepts the pipeline prior to machine code lowering, CodeGen passes that target physical registers, stack frame layouts, or instruction selection (ISel) do not execute.

<Callout type="info" title="Frontend vs Backend Optimization">
Passing `-O2 -emit-llvm` runs the LLVM IR-level optimization pipeline (`opt` pipeline) up through `TargetLibraryInfo` and module optimization passes before emitting the `.ll` or `.bc` file. To inspect raw, unoptimized IR generated directly by Clang's C/C++ frontend prior to any IR optimizations, combine `-emit-llvm` with `-O0` and `-Xclang -disable-O0-optnone`.
</Callout>

## How it works inside Clang

When `-emit-llvm` is specified on the command line:

1. **Driver Phase**: The Clang driver option parser identifies `OPT_emit_llvm` in `clang/include/clang/Driver/Options.td`. In `clang/lib/Driver/ToolChains/Clang.cpp`, the driver inspects flags and appends `-emit-llvm` to the `-cc1` invocation.
2. **Compiler Frontend (`-cc1`)**: `CompilerInvocation::ParseFrontendArgs` in `clang/lib/Frontend/CompilerInvocation.cpp` reads `-emit-llvm` along with `-S` or `-c` to set the `FrontendOptions::ParsedAction`.
   * `-S -emit-llvm` map to `frontend::EmitLLVM`.
   * `-c -emit-llvm` map to `frontend::EmitBC`.
3. **Backend Action dispatch**: In `clang/lib/CodeGen/CodeGenAction.cpp`, `CreateASTConsumer` creates a `BackendConsumer`. Upon completion of AST parsing (`HandleTranslationUnit`), the `BackendConsumer` invokes `EmitBackendOutput` (`clang/lib/CodeGen/BackendUtil.cpp`).
4. **Target Emission Switch**: Inside `EmitBackendOutput`, Clang inspects the requested `BackendAction`. If set to `Backend_EmitLLVM` or `Backend_EmitBC`, it attaches an `llvm::IRPrintingPass` or `llvm::BitcodeWriterPass` to the pass pipeline and bypasses `TargetMachine::addPassesToEmitFile`.

## Related LLVM Optimizations & Backend Mechanisms

**Classification**: Diagnostic / Frontend Action

| Pass / Subsystem | Relationship Label | Description |
| :--- | :--- | :--- |
| `BitcodeWriterPass` | Directly controlled | Emits compressed binary bitcode stream when emitting `.bc`. |
| `PrintModulePass` | Directly controlled | Formats and prints textual LLVM IR module when emitting `.ll`. |
| Target Machine ISel | Bypassed | Instruction Selection and SelectionDAG/GlobalISel pass pipelines are skipped entirely. |

### How to verify

To verify that `-emit-llvm` produces textual LLVM IR or bitcode directly:

```bash
# Generate textual LLVM IR
clang -O2 -S -emit-llvm main.c -o main.ll

# Verify file content starts with LLVM IR syntax (e.g. target datalayout or module attributes)
head -n 10 main.ll

# Generate binary LLVM bitcode
clang -O2 -c -emit-llvm main.c -o main.bc

# Verify file type is LLVM bitcode
file main.bc
```
