| **CC1 option** | None (Driver-only option; does not affect frontend/IR generation) |
| **Optimization level dependency** | O-level does not change driver static linking flags |
| **Default state** | Dynamic linking (`-dynamic` / driver default toolchain behavior) |
| **Category** | Linker / Toolchain Driver Policy |

## What this flag actually does

The `-static` flag is a pure Clang driver-level instruction. It tells the driver toolchain machinery to pass platform-specific static linking arguments to the underlying system linker (such as GNU `ld`, `lld`, or `gold`), preventing the executable from depending on dynamic shared libraries (`.so` or `.dylib`) at runtime.

Because `-static` is entirely consumed by the Clang driver during the linking phase, it has no direct representation inside `-cc1`, generates no LLVM IR attributes, and does not alter target machine instruction generation. If `-c` or `-S` is supplied to Clang, `-static` is effectively ignored during object compilation.

<Callout type="info" title="Driver-Only Scope">
  `-static` does not change code generation for C/C++ source files unless combined with flags that explicitly request Position-Dependent Code (such as `-fno-PIC`). By itself, `-static` instructs `clang` to pass `-Bstatic`, `-static`, or platform-equivalent flags to the linker invocation.
</Callout>

## How it works inside Clang

When Clang processes command-line arguments, `-static` is recognized in the main driver option table and stored as a linker flag flag group option.

### 1. Driver Option Definition
In `clang/include/clang/Driver/Options.td`, `-static` is declared as a flag belonging to `Link_Group`:

```tablegen
def static : Flag<["-"], "static">, Group<Link_Group>, Flags<[NoArgumentUnused]>,
  HelpText<"Bind global references to local definitions when linking">;
```
*(Source link: [`clang/include/clang/Driver/Options.td#L4570-L4575`](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.0/clang/include/clang/Driver/Options.td#L4570))*

### 2. ToolChain Linker Argument Assembly
During the link action construction phase, the Clang driver queries whether `-static` was specified. For ELF targets (such as GNU/Linux), the Gnu toolchain implementation in `clang/lib/Driver/ToolChains/Gnu.cpp` processes the option:

```cpp
if (Args.hasArg(options::OPT_static)) {
  CmdArgs.push_back("-static");
  CmdArgs.push_back("-Bstatic");
}
```
*(Source link: [`clang/lib/Driver/ToolChains/Gnu.cpp#L480-L520`](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.0/clang/lib/Driver/ToolChains/Gnu.cpp#L480-L520))*

The driver translates `-static` into the exact sequence of start-files (`crt1.o`, `crtbeginT.o`) and library link orders (`-Bstatic -lc -lgcc -lgcc_eh`) needed to emit a fully static binary.

## Related LLVM Optimizations & Backend Mechanisms

Classification: **Linker / Toolchain Driver Policy**

| Phase / Mechanism | Relationship | Implementation Details |
| :--- | :--- | :--- |
| **Clang CC1 Frontend** | No direct pass | `-static` is stripped prior to `-cc1` invocation. |
| **LLVM IR Generation** | No direct pass | No LLVM IR attributes or metadata are emitted by `-static`. |
| **Machine Outliner / Codegen** | No direct pass | Instruction selection is completely independent of `-static`. |
| **System Linker (ld / lld)** | Directly controlled | Receives `-static` / `-Bstatic` to enforce resolving dependencies to static archives (`.a`). |

### How to verify driver translation

Run Clang with `-###` to inspect the exact linker command line constructed by the driver:

```bash
clang -### -static main.c -o app
```

In the output for the linker step, notice the inclusion of `-static` / `-Bstatic` and static startup object files (`crtbeginT.o` instead of `crtbeginS.o`).
