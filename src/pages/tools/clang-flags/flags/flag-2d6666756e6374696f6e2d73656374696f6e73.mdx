## What this flag actually does

By default, the compiler places all compiled functions of a translation unit into a single shared code section (typically `.text`). When `-ffunction-sections` is active, the LLVM code generator emits every function into its own individual section (e.g., `.text.used_func` and `.text.unused_func`).

On its own, `-ffunction-sections` does not reduce binary size. Its primary purpose is to expose granular section boundaries to the linker. When combined with garbage-collection linker flags (such as `ld --gc-sections` on ELF platforms or `ld -dead_strip` on macOS), the linker can build an explicit dependency graph of symbol references starting from the entry point (`_start` or `main`) and drop any unreferenced function sections entirely.

<Callout type="warning" title="Trade-offs: Binary overhead and metadata size">
Placing every function in a distinct section increases object file overhead. It creates additional section header table entries, relocations, and debug info records within intermediate `.o` files. Furthermore, it can slightly reduce instruction cache locality if the linker does not reorder sections effectively.
</Callout>

### Defaults across optimization levels

Optimization levels (`-O0`, `-O2`, `-O3`, `-Os`, `-Oz`) **do not automatically enable** `-ffunction-sections` on standard Linux target triples (`x86_64-unknown-linux-gnu`). It must be passed explicitly.

## How it works inside Clang

The flag flows from driver options down to target machine configuration via `CodeGenOptions`:

1. **Driver Parsing**: Clang's driver processes `-ffunction-sections` in `clang/lib/Driver/ToolChains/Clang.cpp` and translates it into the internal CC1 flag `-ffunction-sections`.
   * Source reference: [clang/lib/Driver/ToolChains/Clang.cpp#L5085](https://github.com/llvm/llvm-project/blob/main/clang/lib/Driver/ToolChains/Clang.cpp#L5085)
2. **Frontend CodeGenOptions**: `CompilerInvocation` sets `CodeGenOpts.FunctionSections = 1`.
   * Source reference: [clang/lib/Frontend/CompilerInvocation.cpp#L1615](https://github.com/llvm/llvm-project/blob/main/clang/lib/Frontend/CompilerInvocation.cpp#L1615)
3. **LLVM TargetOptions Propagation**: When creating the `TargetMachine`, Clang populates LLVM's target configuration: `TargetOpts.FunctionSections = CodeGenOpts.FunctionSections`.
   * Source reference: [clang/lib/CodeGen/BackendUtil.cpp#L518](https://github.com/llvm/llvm-project/blob/main/clang/lib/CodeGen/BackendUtil.cpp#L518)
4. **AsmPrinter / TargetLoweringObjectFile**: During backend assembly generation, LLVM queries `TargetLoweringObjectFile::getSectionForFunction()`. Instead of returning the standard default `.text` section, it constructs a unique section name formatted as `.text.<function_name>`.
   * Source reference: [llvm/lib/Target/TargetLoweringObjectFile.cpp#L361](https://github.com/llvm/llvm-project/blob/main/llvm/lib/Target/TargetLoweringObjectFile.cpp#L361)

## Related LLVM Optimizations & Backend Mechanisms

Classification: **backend/codegen**

| Mechanism | Relationship Label | Description |
| :--- | :--- | :--- |
| **TargetLoweringObjectFile** | Directly controlled | Emits explicit `.section .text.<name>` directives for each function symbol. |
| **`-fdata-sections`** | Related mechanism | Emits global variables into dedicated data sections (`.data.<name>` / `.bss.<name>`). |
| **Linker GC (`--gc-sections`)** | Backend mechanism | Linker pass that traces symbol graphs and strips unreferenced sections emitted by this flag. |

### How to verify backend behavior

You can verify section assignment by inspecting emitted assembly directives:

```bash
clang -S -O2 -ffunction-sections example.cpp -o - | grep -E "^\s*\.section"
```

Expected output showing individual section directives:
```assembly
    .section    .text.used_func,"ax",@progbits
    .section    .text.unused_func,"ax",@progbits
```
