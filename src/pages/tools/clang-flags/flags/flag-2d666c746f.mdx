## At a glance

| Attribute | Value |
| :--- | :--- |
| **Architectures** | Architecture-independent (All target triples supported by Clang/LLVM) |
| **Category** | Code Generation / Link-Time Optimization |
| **Compiler Support** | Clang 3.0+ (`-flto`), default full LTO mode |
| **Optimization Level** | Active at all optimization levels (typically paired with `-O2` or `-O3`) |
| **Risk / Side Effects** | Significantly increased link time, massive memory consumption during linking, single-threaded backend pipeline unless configured |

## What this flag actually does

Passing `-flto` alters both the frontend compilation phase and the linker invocation phase:

1. **Compilation Phase (`clang -c -flto`)**: Instead of compiling C/C++ source code down to native machine code (`.o` containing ELF/Mach-O native text), Clang emits LLVM IR bitcode wrapped inside an object container (or raw `.bc` files). In `-cc1`, this manifests as passing `-flto-unit` and `-emit-llvm-bc`.
2. **Link Phase (`clang -flto main.o lib.o -o app`)**: When invoked as a driver for linking, Clang automatically appends plugin arguments to the system linker (`lld`, `ld64`, or `gold` via `LLVMgold.so`) to process bitcode files. Under **Full LTO** (`-flto` or `-flto=full`), the linker reads all bitcode module inputs, merges them into a single monolithic LLVM Module (`llvm::Linker`), performs interprocedural optimizations (IPO) across all translation units (such as cross-TU inlining, devirtualization, and dead-argument elimination), and then runs codegen for the entire program at once.

This is distinct from `-flto=thin` (ThinLTO), which compiles modules independently while exchanging global summary indexes for parallel, distributed optimization.

```
                  ┌──────────────┐      ┌──────────────┐
                  │  file1.cpp   │      │  file2.cpp   │
                  └──────┬───────┘      └──────┬───────┘
                         │ -flto -c            │ -flto -c
                         ▼                     ▼
                  ┌──────────────┐      ┌──────────────┐
                  │ file1.o (BC) │      │ file2.o (BC) │
                  └──────┬───────┘      └──────┬───────┘
                         └──────────┬──────────┘
                                    │ ld.lld -flto
                                    ▼
                         ┌────────────────────┐
                         │  llvm::Linker      │
                         │  (Monolithic LTO)  │
                         └──────────┬─────────┘
                                    │ Cross-TU Inlining & IPO
                                    ▼
                         ┌────────────────────┐
                         │ Target Machine CG  │
                         └──────────┬─────────┘
                                    │
                                    ▼
                         ┌────────────────────┐
                         │ Native Binary Exec │
                         └────────────────────┘
```

:::note Bitcode Wrappers vs Raw Bitcode
When building with `clang -flto -c foo.c -o foo.o`, the generated file is actually an ELF (or Mach-O/COFF) file containing a special section (`.llvmbc`) that holds the bitcode payload. This allows symbol resolution tools (`ar`, `nm`) to recognize symbols if an LTO-aware plugin is available.
:::

## Minimal realistic example

Consider two separate translation units where a caller calls an external function that returns a constant multiplier:

<SourceCode
  language="cpp"
  title="helper.cpp & main.cpp"
  code={`// helper.cpp
int get_multiplier() {
    return 42;
}

// main.cpp
extern int get_multiplier();

int calculate(int value) {
    return value * get_multiplier();
}`}
/>

Without `-flto`, `main.cpp` cannot inspect the body of `get_multiplier()`. It must emit a dynamic dynamic or static function call (`call get_multiplier`).

With `-flto`, the linker merges `helper.cpp` and `main.cpp` bitcode into a single module prior to running the optimization pipeline.

## Before vs. after assembly

Below is the disassembly of `calculate()` in the final binary after linking `main.o` and `helper.o` with `-O2`:

<AsmDiff
  before={`# Non-LTO Binary (clang -O2 main.cpp helper.cpp)
calculate(int):
        push    rax
        call    get_multiplier()@PLT
        imul    eax, edi
        pop     rcx
        ret`}
  after={`# Full-LTO Binary (clang -O2 -flto main.cpp helper.cpp)
calculate(int):
        imul    eax, edi, 42
        ret`}
/>

### What changed?
1. **Cross-TU Inlining**: The optimizer resolved `get_multiplier()` across file boundaries, eliminated the call overhead, and folded the return value `42`.
2. **Instruction Reduction**: The function stack frame setup (`push rax`, `pop rcx`) was completely eliminated, leaving a single `imul` instruction.

## Why use it / when not to use it

### Advantages
- **Whole-Program Inlining**: Removes abstraction penalties across static library and translation unit boundaries.
- **Aggressive Devirtualization**: Analyzes class hierarchies across the entire application to turn virtual calls into direct calls or inline them.
- **Global Dead Code Elimination**: Strips unreferenced functions, structures, and static variables that cannot be safely purged at individual TU scope.
- **Type Metadata / CFI Support**: Full LTO enables Control Flow Integrity (`-fsanitize=cfi`) by providing global visibility of pointer types across the program.

### When NOT to use it
- **Iterative Local Development**: Full LTO forces a single-threaded (or heavily bottlenecked) link phase that rebuilds and re-optimizes the entire codebase on every small change.
- **Memory-Constrained Build Workers**: Linking multi-million-line C++ targets with Full LTO can consume tens to hundreds of gigabytes of RAM during the `llvm::Linker` merge phase. Use `-flto=thin` instead.
- **Pure Dynamic Shared Libraries with Weak Symbol Overrides**: Cross-module optimizations assume symbol visibility rules specified by export maps; overly aggressive LTO can inline functions intended to be interposed at runtime.

## Performance impact

Qualitatively, Full LTO produces near-optimal code generation across translation unit boundaries:

- **Runtime Execution**: Typically yields a **1% to 10% performance gain** over non-LTO binaries due to cross-module inlining, better register allocation across call sites, and global dead-code stripping.
- **Binary Size**: Can reduce binary size significantly by dropping unused non-exported functions, or increase binary size if inlining limits are tuned aggressively.
- **Build Bottleneck**: Unlike ThinLTO, which scales linearly across CPU cores, Full LTO performs module merging and global optimization in a centralized pipeline stage, drastically increasing link-time CPU and memory footprints.

## Compatibility

| Environment / Toolchain | Compatibility Level |
| :--- | :--- |
| **LLD Linker (`ld.lld`)** | First-class native support; no external plugin required. |
| **GNU gold (`ld.gold`)** | Requires `LLVMgold.so` plugin loaded via `-fuse-ld=gold`. |
| **Apple `ld64` / `lldb`** | Supported natively via libLTO.dylib framework. |
| **MSVC / `link.exe` / `lld-link`** | Supported (`-flto` maps to LLVM bitcode embedded in COFF objects). |

## Usage example

### Standard Compiling and Linking with Clang Driver

```bash
# Step 1: Compile source files to bitcode objects
clang++ -O3 -flto -c main.cpp -o main.o
clang++ -O3 -flto -c helper.cpp -o helper.o

# Step 2: Link bitcode objects with LTO enabled
clang++ -O3 -flto main.o helper.o -o app
```

### Inspecting Driver Lowering to CC1 and Linker

To inspect how `-flto` translates to frontend flags and linker invocations:

```bash
clang++ -O2 -flto -### main.cpp -o app
```

Key driver-generated flags observed:
- **Frontend (`cc1`)**: `-flto-unit`, `-emit-llvm-bc`
- **Linker Driver (`ld.lld`)**: `-plugin-opt=O2` (passes optimization level to the LTO engine)

## Adjacent options

- `-flto=thin`: Enables ThinLTO, providing ~95% of Full LTO's performance benefits with fast, highly parallelized link times and significantly lower memory requirements.
- `-fno-lto`: Explicitly disables LTO bitcode generation and reverts to native object output.
- `-flto-jobs=N`: Controls the number of parallel threads used during the LTO backend code generation phase.
- `-fwhole-program-vtables`: Enables whole-program virtual table optimizations (requires `-flto`).

## How it works inside Clang

| Pipeline Stage | Mechanism & Behavior |
| :--- | :--- |
| **Driver Options Parsing** | `-flto` is parsed in `clang/lib/Driver/ToolChains/Clang.cpp`. The driver sets `types::TY_LLVM_BC` as output or enables bitcode embedding in object files. |
| **Frontend Options (`cc1`)** | Passes `-emit-llvm-bc` or configures `CodeGenOptions::PrepareForLTO`. Sets `-flto-unit` to embed type metadata for CFI/WholeProgramDevirt. |
| **LLVM IR Generation** | `clang::EmitBackendOutput` writes bitcode to the destination `.o` file instead of passing the module to the target machine code generator. |
| **Linker Integration** | During link step, LTO plugin (`libLTO` or LLD internal LTO engine) invokes `llvm::lto::LTO::run()` to merge modules, run IR pass pipeline, and emit final object. |
