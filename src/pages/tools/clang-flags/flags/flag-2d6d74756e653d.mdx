## What this flag actually does

The `-mtune=` flag controls microarchitectural optimizations in LLVM's code generator without altering the target Instruction Set Architecture (ISA). Unlike `-march=` or `-mcpu=`, which enable target-specific vector/crypto extensions and render binaries incompatible with older hardware, `-mtune=` strictly adjusts cost models, instruction scheduling latencies, pipeline hazard avoidance, branch alignment, and machine-level instruction fusion.

When passed to the driver, `-mtune=<cpu>` translates into target-specific backend target features (such as `+tune-cpu=<cpu>`) or target-cpu attributes in LLVM IR. 

Key backend parameters governed by `-mtune=`:
- **Instruction Scheduling**: Reorders assembly instructions based on the pipeline depth, execution port distribution, and functional unit latencies of the tuned core.
- **Instruction Selection & Fusion**: Prefers macro-fusion pairs (e.g., `cmp` + `jmp` on modern x86 cores) or micro-fusion opportunities.
- **Loop & Unrolling Heuristics**: Adjusts software pipelining costs, unroll factors, and loop vectorization cost models.
- **Memory & Alignment**: Adjusts preferred branch target alignment, code block padding, and cache line prefetch behavior.

```
       -march=x86-64-v2 (Sets ABI baseline: SSE4.2, POPCNT)
              │
              ├── -mtune=generic (Default scheduling/cost model)
              │
              └── -mtune=znver3  (Optimized pipeline scheduling for AMD Zen 3; same binary ISA)
```

:::note
If `-mcpu=` is specified, it sets both the target ISA capabilities and the tuning target. Specifying `-mtune=` explicitly overrides the tuning target while keeping the target ISA unchanged.
:::

## Why use it / when not to use it

### Recommended Use Cases
- **Generic Binary Distribution with Target Fleet Tuning**: When building binaries that must run on older baseline hardware (e.g., standard x86-64-v2 cloud instances) but the majority of your deployment fleet runs on a specific newer generation (e.g., `znver3` or `neoverse-n1`).
- **Performance Profiling**: Isolating pipeline bottleneck differences across microarchitectural generations without dealing with ISA capability drift.

### When Not to Use It
- **When `-march=` or `-mcpu=` is already precise**: If you are compiling locally for host hardware using `-march=native` or `-mcpu=native`, `-mtune=` is already set implicitly to match your machine.
- **Target cross-compilation without ISA restrictions**: If your code will strictly run on a controlled microarchitecture, use `-mcpu=<target>` (ARM/RISC-V) or `-march=<target>` (x86) to allow full ISA extensions (AVX-512, SVE, BMI2) alongside microarchitecture tuning.

---

## Performance impact

`-mtune=` yields purely qualitative, execution-pipeline-level trade-offs:

- **Positive Impact**: Better hardware resource utilization (execution ports, load/store queues, latency hiding) on the specified microarchitecture.
- **Negative/Neutral Impact**: On legacy or non-matching hardware architectures, tuned code remains 100% functionally correct, but instruction reordering or aggressive loop unrolling tuned for a wide out-of-order pipeline may cause minor register pressure or cache footprint overhead on narrower cores.

## Usage example

```bash
# 1. Target a generic x86-64 baseline while tuning pipeline for Intel Sapphire Rapids
clang++ -O3 -march=x86-64-v3 -mtune=sapphirerapids -c core_loop.cpp -o core_loop.o

# 2. Cross-compiling for ARMv8-A baseline, tuned specifically for AWS Graviton2 (Neoverse-N1)
clang -O3 --target=aarch64-linux-gnu -march=armv8-a -mtune=neoverse-n1 service.c -o service

# 3. Inspecting the exact driver flag forwarding and backend feature strings
clang -O2 -mtune=znver3 -### -c test.c
```

## Adjacent options

- **`-march=`**: Defines the minimum baseline Instruction Set Architecture (ISA) available to the compiler.
- **`-mcpu=`**: On architectures like AArch64 and PowerPC, sets both the baseline target ISA (`-march=`) and the microarchitectural tuning (`-mtune=`) simultaneously.
- **`-mtune=generic`**: Resets microarchitecture tuning back to LLVM's balanced, target-agnostic cost model.

## How it works inside Clang

| Compilation Stage | Component | Execution / Transformation |
| :--- | :--- | :--- |
| **Driver Options** | `clang/include/clang/Driver/Options.td` | Driver parses `-mtune=` via `Joined<["-"], "mtune=">`. |
| **Driver Translation** | `clang/lib/Driver/ToolChains/Arch/` | Target-specific driver logic (e.g., `X86.cpp`, `AArch64.cpp`) translates the tuned CPU name into target features (`+tune-cpu=...`) or LLVM IR attributes. |
| **LLVM IR Generation** | `clang/lib/CodeGen/CodeGenModule.cpp` | Emits `"tune-cpu"="<cpu_name>"` as a function-level IR attribute on generated functions. |
| **LLVM Target Backend** | `llvm/lib/Target/<Arch>/` | Subtarget features query the core-specific `ProcessorModel` defined in TableGen (`.td`) files to populate `TargetSchedModel` and `TargetTransformInfo`. |
