## Register layout before and after

Under the standard AAPCS64 ABI, `x10` sits in the volatile "scratch" block. This flag moves it into the saved set.

<Callout tone="danger" title="x10 moves">
  `x10` leaves the caller-saved scratch block and becomes callee-saved, joining `x19`–`x28`. Functions that touch `x10` now spill and restore it in the prologue/epilogue.
</Callout>

## What this flag actually does

`-fcall-saved-x10` promotes the general-purpose register `x10` from a **caller-saved** (volatile) register to a **callee-saved** register on AArch64. After this flag is applied, any function that uses `x10` is responsible for preserving its value across calls, and the compiler is free to keep live values in `x10` for the whole lifetime of a call sequence without reloading them afterwards.

The effect is visible in the generated prologue and epilogue. Consider this loop, which keeps a pointer and a counter live across calls to `external_fn`:

<SourceCode
  file="test/main.cpp"
  flag="-fcall-saved-x10"
  language="c"
  code={`int sum_with(int *arr, int n) {
    int total = 0;
    int *p = arr;
    for (int i = 0; i < n; i++) {
        total += *p;
        external_fn(total);
        p++;
    }
    return total;
}`}
  note="The flag was applied to this translation unit. With the default ABI the loop counter must live in a true callee-saved register (w19/w21); with -fcall-saved-x10 the backend is allowed to keep it in w10 across the call."
/>

With `-fcall-saved-x10`, the loop counter lives in `w10` across the call — impossible under the default ABI, which would force the compiler to use a dedicated callee-saved register instead.

## Why would anyone use this?

`-fcall-saved-x10` is a niche, ABI-level tuning knob. It shows up almost exclusively in **low-level systems code** where the register layout is already custom:

- **Embedded firmware** with hand-written startup code or interrupts that already preserve `x10`.
- **JIT compilers and runtime systems** that generate machine code against a custom calling convention and want a wider set of call-preserved registers.
- **Hypervisors and kernels** with their own register conventions (e.g. preserving an extra register across a controlled call boundary).
- **Custom ABIs** where the contract already treats `x10` as callee-saved, letting Clang-generated code match assembly written by hand.

<Callout tone="warning" title="Not for normal application development">
  Everyday application code compiled for the standard AArch64 ABI should **never** use this flag. It exists to make the compiler conform to an already-custom ABI, not to hand you free registers.
</Callout>

## Performance impact

**Advantages**

- **Fewer reloads for hot paths:** a value kept in `x10` across many calls is spilled once in the prologue and restored once in the epilogue, instead of being reloaded from the stack before each call.
- **Better register allocation:** an extra call-preserved register gives the register allocator more stable homes for long-lived values, which can shorten hot loops.

**Disadvantages**

- **Larger prologue/epilogue:** every function that uses `x10` now spills and reloads it (`str x10` / `ldr x10`), adding two memory ops and growing the frame.
- **More stack usage:** the spill slot consumes stack space that the default ABI does not need.
- **ABI incompatibility:** objects built with the flag cannot interoperate with objects built without it unless both sides agree `x10` is preserved.

In practice, for a value that survives only one or two calls, the flag is a wash or a small loss — the single prologue spill costs about as much as the reloads it removes. It wins when the same value crosses **many** calls (tight loops over external functions).

## When to use it

- **Custom calling conventions**: when you are building or linking against hand-written assembly, a JIT, or a runtime with its own ABI that already treats `x10` as callee-saved, this flag makes compiler-generated code match that expectation.
- **Keeping state in `x10` across calls**: if hot code wants to hold a frequently used pointer or accumulator in `x10` and all callees are compiled with the same flag, the value survives calls without per-call reloads, trading one prologue/epilogue spill for what would otherwise be repeated save/reload work.
- **Consistent recompilation**: the flag only helps if every function in the call chain that might clobber `x10` is built with it (or is known to preserve `x10`), since a plain AAPCS callee is free to overwrite it.

## When not to use it

- **Mixing with default-ABI code**: if any callee is compiled without this flag (libraries, system code, or a separate translation unit), `x10` will not actually survive that call, producing subtle wrong-code bugs. Apply it to an entire build, or not at all.
- **On non-AArch64 targets**: the option is rejected outright, e.g. `clang: error: unsupported option '-fcall-saved-x10' for target 'x86_64-none-elf'`.
- **When scratch registers are scarce**: promoting `x10` to callee-saved removes it from the volatile scratch pool (`x9`–`x15`), which can increase register pressure and add spills elsewhere in functions that relied on it as a temporary.
- **For portability**: this is a Clang/AArch64-specific option. Neither the x86 targets nor GCC accept it, so it cannot appear in portable build recipes.

## Register lifetime across a call

```
Function entry
   │
   ▼
str x10, [sp, #-48]!        ← prologue spills x10 (it is now callee-saved)
   │
   ▼
... uses x10 for live state ...
   │
   ├──▶ bl  external_fn     ← x10 survives; the callee is expected to preserve it
   │
   ▼
... continues using x10 ...
   │
   ▼
ldr x10, [sp], #48          ← epilogue restores x10
   │
   ▼
ret
```

Without the flag, `x10` could not hold live state across the `bl` — the compiler would have reloaded it after the call or moved it to a saved register.

## Compatibility

| Compiler / target | `-fcall-saved-x10` |
| --- | --- |
| Clang, AArch64 | Yes |
| Clang, x86 / other targets | No (rejected) |
| GCC | No |
| MSVC | No |

<Callout tone="danger" title="Warning: ABI change">
  Changing caller/callee saved registers changes the ABI. Only use this flag when **every linked object** follows the same convention — mixing a default-ABI library with `-fcall-saved-x10` code silently corrupts `x10` across calls. Measure before and after; for most code the prologue spill makes it a net loss.
</Callout>

## Usage example

Target an AArch64 triple explicitly, since the flag is rejected on other targets:

```bash
clang --target=aarch64-none-elf -O2 -fcall-saved-x10 main.cpp -o app
```

`-fcall-saved-x10` is a driver flag; the backend receives it as the `+call-saved-x10` target feature, so it does **not** need `-Xclang` forwarding. Verify it took effect by inspecting the prologue of a function that uses `x10`:

```bash
clang --target=aarch64-none-elf -O2 -fcall-saved-x10 -S main.cpp
# look for: str x10, [sp, #-N]!
```

## Adjacent options

- `-fcall-saved-x8`, `-fcall-saved-x9`, `-fcall-saved-x11` … `-fcall-saved-x15`, `-fcall-saved-x18` — same mechanism for other registers.
- `-fcall-used-x10` — inverse: mark a register as caller-saved even if the ABI says otherwise.
- `-ffixed-x10` — reserve `x10` entirely, so the compiler never allocates it (relevant when inline assembly owns the register).
- `-mllvm -max-reserved-regs` — tune how many registers the backend treats as reserved, affecting the same allocation decisions.

## How it works inside Clang

The option is defined as a member of the AArch64 features group in `clang/include/clang/Driver/Options.td` (line 5371):

```text
def fcall_saved_x10 : Flag<["-"], "fcall-saved-x10">,
    Group<m_aarch64_Features_Group>,
    HelpText<"Make the x10 register call-saved (AArch64 only)">;
```

At driver time, `getAArch64TargetFeatures()` in `clang/lib/Driver/ToolChains/Arch/AArch64.cpp` translates the presence of the option into the subtarget feature string `+call-saved-x10`, which is passed to the backend. There it is parsed by `AArch64Subtarget`, which records the register in its `CustomCallSavedXRegs` bit vector. Finally, in `AArch64RegisterInfo::UpdateCustomCalleeSavedRegs()` and `UpdateCustomCallPreservedMask()`, `x10` is appended to both the callee-saved register list (so the prologue/epilogue spills it) and the call-preserved mask (so the register allocator and call lowering treat it as preserved).
