## What this flag actually does

The `-march=` option dictates the explicit Instruction Set Architecture (ISA) target tier, base architecture revision, and optional architectural features for backend code generation. 

Unlike `-mtune=`, which adjusts scheduling models and pipeline costs without introducing non-baseline instructions, `-march=` directly alters instruction availability. It authorizes the LLVM backend selection DAG/GlobalISel stages to emit instructions, vector registers, and addressing modes specific to that architecture or extension set.

### Target-Specific Semantics

The syntax and behavioral impact of `-march=` vary fundamentally across target architectures:

*   **x86 / x86-64**: Configures both the architectural generation and implied microarchitectural feature set (e.g., `-march=haswell`, `-march=x86-64-v3`, `-march=native`). On x86, `-march=` implies both instruction availability and default microarchitectural tuning.
*   **AArch64**: Sets the base architecture version and optional extension modifiers (e.g., `-march=armv8.2-a+crypto+fp16+sve`).
*   **RISC-V**: Defines the exact RISC-V ISA string according to the RISC-V unprivileged specification, including base integer model and standard/custom extensions (e.g., `-march=rv64gc`, `-march=rv64imafcv_zba_zbb`).
*   **ARM (32-bit)**: Selects the ARM architecture profile and architecture version (e.g., `-march=armv7-a`, `-march=armv8-m.main`).

### Driver Execution & Target Translation

The Clang driver parses `-march=`, resolves architecture-specific feature aliases, and passes low-level target features down to `clang -cc1` via `-target-cpu` and `-target-feature` flags.

```text
Host Call:
  clang -march=x86-64-v3 -O3 -c example.c

Driver Translation (-cc1 invocation):
  clang -cc1 -triple x86_64-unknown-linux-gnu \
    -target-cpu x86-64-v3 \
    -target-feature +avx \
    -target-feature +avx2 \
    -target-feature +bmi \
    -target-feature +bmi2 \
    -target-feature +fma \
    ...
```

:::caution Portability / target mismatch
Binaries built with a newer ISA than the execution CPU (including `-march=native` on a developer host that is richer than production) can trap with `SIGILL` when an unsupported opcode path runs. That is a **deployment / target mismatch**, not a silent correctness UB from the flag itself. `-march=native` is **host-specific** — never treat one machine’s feature set as universal.
:::

## Minimal realistic example

The C code below demonstrates vector reduction across a array of single-precision floating point values:

<SourceCode 
  language="cpp"
  code={`void vector_sum(const float* __restrict src, float* __restrict dst, int count) {
    for (int i = 0; i < count; ++i) {
        dst[i] = src[i] * 2.0f + 1.0f;
    }
}`}
/>

When compiled for baseline x86-64 (`-march=x86-64`), the auto-vectorizer emits SSE2 instructions (using `addps` / `mulps`). When compiled with `-march=x86-64-v3` or `-march=haswell`, the backend replaces SSE pairs with 256-bit AVX2 vector instructions and fused multiply-add (`vfmadd213ps`).

## Before vs. after assembly

Illustrative **x86_64** shape comparing baseline (`-march=x86-64`) against AVX2/FMA (`-march=x86-64-v3`). Exact instruction selection is **compiler-version and triple dependent** — verify with your `clang -S` before citing counts or latencies.

<AsmDiff 
  before={`# -march=x86-64 -O2 (Baseline x86-64 / SSE2)
.LBB0_2:
    movups  (%rdi,%rax,4), %xmm0
    movups  16(%rdi,%rax,4), %xmm1
    mulps   %xmm2, %xmm0
    mulps   %xmm2, %xmm1
    addps   %xmm3, %xmm0
    addps   %xmm3, %xmm1
    movups  %xmm0, (%rsi,%rax,4)
    movups  %xmm1, 16(%rsi,%rax,4)
    addq    $8, %rax
    cmpq    %rcx, %rax
    jl      .LBB0_2`}
  after={`# -march=x86-64-v3 -O2 (AVX2 + FMA Enabled)
.LBB0_2:
    vmovups (%rdi,%rax,4), %ymm1
    vmovups 32(%rdi,%rax,4), %ymm2
    vfmadd213ps %ymm0, %ymm3, %ymm1
    vfmadd213ps %ymm0, %ymm3, %ymm2
    vmovups %ymm1, (%rsi,%rax,4)
    vmovups %ymm2, 32(%rsi,%rax,4)
    addq    $16, %rax
    cmpq    %rcx, %rax
    jl      .LBB0_2`}
/>

### Important difference
On this x86-64 example, baseline keeps 128-bit `%xmm` SSE ops; `-march=x86-64-v3` can use 256-bit `%ymm` AVX2 plus FMA (`vfmadd213ps`). That changes **instruction availability and register width**, not a universal “2× faster” guarantee — measure on the real deployment CPU.

## Why use it / when not to use it

### Recommended Use Cases

1. **Targeted Deployment to Known Hardware**: When building microservices or HPC workloads deployed to homogeneous server fleets (e.g., AWS Graviton3 with `-march=armv8.4-a+sve` or Xeon Ice Lake with `-march=icelake-server`).
2. **Exploiting Hardware Vector Units**: Enabling autovectorization for specialized SIMD/vector ISAs such as AVX-512, Arm SVE/SVE2, or RISC-V Vector (`rv64gcv`).
3. **Local Developer Builds**: Using `-march=native` during iterative local builds maximizes instruction set utilization on the host hardware.

### Anti-Patterns and Prohibitions

1. **Generic Software Distribution**: Packaging binaries meant for general distribution (Linux distros, macOS, Windows client applications) with aggressive `-march=` options risks crashing end-user machines lacking those instructions.
2. **Multi-Architecture Support without Function Multiversioning**: If host CPU feature checking is required at runtime, use target attributes (`__attribute__((target("...")))`) or `__builtin_cpu_supports()` instead of global compilation flags.
3. **Replacing Microarchitectural Tuning**: Do not use `-march=` if your goal is solely to tune scheduling for a specific CPU architecture without breaking backwards compatibility. Use `-mtune=` instead.

---

## Performance impact

`-march=` changes **which instructions the backend may emit**. Wider SIMD or specialty opcodes can help vector-heavy code on matching hardware, but gains are **workload- and CPU-specific** — do not treat one host’s `-march=native` result as portable evidence.

*   **Vectorization capacity**: Newer ISA levels can expose wider registers (e.g. SSE → AVX2 → AVX-512 on x86). Whether that improves wall time depends on the loop, memory bandwidth, and the execution CPU.
*   **Specialty ops**: Features like `+bmi2`, `+crypto`, or `+zbb` can replace multi-instruction sequences when the target and CPU both support them.
*   **Frequency / thermal effects**: Some x86 generations downclock under heavy AVX-512; profile on the **deployment** microarchitecture, not only the build host.

## Usage example

```bash
# Compile for standard x86-64 microarchitecture level 3 (AVX2, FMA, BMI1/2, LZCNT)
clang++ -O3 -march=x86-64-v3 -c workload.cpp -o workload.o

# Target ARMv8.4-A with SVE and Crypto extensions
clang++ -O3 --target=aarch64-linux-gnu -march=armv8.4-a+sve+crypto -c crypto.cpp

# Target RISC-V 64-bit with GC base extensions + Bit Manipulation
clang -O2 --target=riscv64-unknown-elf -march=rv64gc_zba_zbb -c algorithm.c

# Inspect host CPU detection when using -march=native
clang -march=native -### -E - < /dev/null 2>&1 | grep -E "(-target-cpu|-target-feature)"
```

## How it works inside Clang

| Pipeline Stage | Implementation Details |
| :--- | :--- |
| **Driver Option Parsing** | `clang/include/clang/Driver/Options.td` defines `-march=`. Parsed by `clang::driver::Driver`. |
| **Target Driver Translation** | Target-specific driver logic (e.g., `clang/lib/Driver/ToolChains/Arch/X86.cpp`, `AArch64.cpp`, `RISCV.cpp`) resolves the architecture string into specific target CPUs and feature sets. |
| **Frontend Options Pass** | Driver translates `-march=` into `-target-cpu <cpu>` and explicit `-target-feature +<feature>` / `-target-feature -<feature>` arguments for the `clang -cc1` execution phase. |
| **LLVM Target Machine Setup** | `llvm::TargetMachine` initializes the `MCSubtargetInfo` and backend target triples. |
| **Instruction Selection** | SelectionDAG and GlobalISel consult `Subtarget.hasFeature(...)` to enable architecture-specific node patterns during lowering. |

## Related LLVM Optimizations & Backend Mechanisms

**Flag category:** Backend / target CPU feature selection. Not an IR “optimization pass”, though it enables ISA-specific codegen and may unlock vectorization profitability.

| Mechanism | Stage | Relationship | Effect |
| :--- | :--- | :--- | :--- |
| Target CPU / feature flags | Driver → TargetMachine | Directly controlled | Sets `target-cpu` / `target-features` |
| Instruction selection | Machine backend | Backend mechanism | May emit ISA-specific instructions |
| Cost models for vectorize/unroll | LLVM IR | Indirectly affected | Passes still run; profitability changes with features |

### How to verify

```bash
clang -O2 -march=native -S -emit-llvm w.c -o n.ll
rg 'target-cpu|target-features' n.ll
clang -### -march=haswell -c w.c 2>&1 | rg target-cpu\|target-feature
```
