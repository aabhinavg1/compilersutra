## What does `-Os` actually do?

`-Os` tells Clang to optimize with code size as an important consideration.

The objective is not simply to generate the fewest instructions. It is to generate compact code while retaining transformations that provide useful runtime benefits.

The compiler may make different decisions about inlining, loop transformations, vectorization, and instruction selection depending on the optimization level and target.

For example, an inlined function may remove call overhead but duplicate instructions at several call sites. A loop transformation may improve execution time but increase the amount of generated machine code.

With `-Os`, the compiler accounts for these trade-offs.

<Callout tone="warning" title="No universal guarantees">
  `-Os` does **not** guarantee a smaller executable, scalar loops, disabled vectorization, or performance close to `-O2`. Those outcomes depend on the program, target, compiler version, and build configuration. This page shows what **one** Clang 18.1.3 / x86_64 experiment measured — not a law of LLVM.
</Callout>

## How `-Os` differs from other optimization levels

| Flag | General intent |
| :--- | :--- |
| `-O0` | Minimize optimization work, primarily for development and debugging |
| `-O1` | Apply a moderate set of optimizations |
| `-O2` | Apply a broad set of optimizations intended for good runtime performance |
| `-O3` | Enable additional and more aggressive performance-oriented optimizations |
| `-Os` | Optimize with an emphasis on code size while retaining useful performance optimizations |
| `-Oz` | Prioritize reducing code size more aggressively, potentially sacrificing more runtime performance |

These descriptions communicate the **intent** of each level, not a guarantee that one level always produces faster or smaller code than another.

## A minimal C++ workload

We use a simple buffer transformation to examine how optimization levels affect generated code.

<SourceCode
  file="process_buffer.cpp"
  flag="-Os"
  language="cpp"
  code={`#include <cstddef>
#include <cstdint>

void process_buffer(std::uint32_t* buffer, std::size_t length) {
    for (std::size_t i = 0; i < length; ++i) {
        buffer[i] = (buffer[i] ^ 0x5A5A5A5Au) + 1u;
    }
}`}
  note="Inspection kernel only. The timed csperf workload wraps this loop with a 4M-element buffer and 24 passes (see static/files/clang-flags/-Os/)."
/>

Depending on the target and compiler settings, LLVM may generate scalar instructions, vector instructions, or another equivalent sequence.

Do not assume that `-O2` must vectorize this loop or that `-Os` must keep it scalar. Inspect the generated output to find out.

## Understanding the LLVM IR attributes

On this Clang 18.1.3 build:

| Artifact | Size-related attributes on `process_buffer` |
| :--- | :--- |
| `loop-O2.ll` | none (`optsize` / `minsize` absent) |
| `loop-Os.ll` | `optsize` |
| `loop-Oz.ll` | `minsize` and `optsize` |

```bash
grep -nE 'optsize|minsize' loop-O2.ll loop-Os.ll loop-Oz.ll
```

### `optsize`

Indicates a preference for smaller generated code, especially where that can be achieved without significantly affecting performance.

### `minsize`

Communicates a stronger preference for minimizing code size.

These attributes are not interchangeable, and neither guarantees a particular number of instructions or bytes. Attribute placement can vary across LLVM releases — always inspect your own IR.

## How to interpret these results

### Size

`-Os` cut the kernel object text from 195 B to 79 B (~60% smaller) by dropping the SSE vector body. The full executable text shrank modestly (2860 → 2676 B); on-disk size matched `-O2` after page alignment.

### Runtime

`-Os` ran ~3× slower than `-O2`; `-Oz` ~4.5× slower. Instruction counts rose sharply without vectorization — enough to dominate wall time on this memory-bandwidth-friendly XOR/add loop. Higher IPC under `-Os` did **not** mean a faster program: more instructions still took more cycles.

### What this does *not* prove

- That `-Os` always disables vectorization (other loops/targets may still vectorize).
- That `-Os` is always slower (I-cache sensitive apps can go the other way).
- That `-Oz` is always smallest at link time (this bench shows the opposite for the final ELF).

## When should you use `-Os`?

### Good candidates

- Firmware and embedded applications with constrained storage
- Libraries where reducing code footprint matters
- Applications with significant cold code or instruction-footprint constraints
- Programs where **your** measurements show an acceptable performance trade-off

### When to evaluate alternatives

- Compute-heavy workloads where vectorization or loop transforms dominate (as in this buffer kernel)
- Latency-sensitive code with strict performance requirements
- Applications where executable size is not a meaningful constraint
- Workloads where `-Oz` produces a smaller binary with an acceptable runtime cost — **verify** with `size` and a timer

## Compatibility and usage

```bash
clang++ -O2 -c process_buffer.cpp -o loop-O2.o
clang++ -Os -c process_buffer.cpp -o loop-Os.o
clang++ -Oz -c process_buffer.cpp -o loop-Oz.o
size loop-O2.o loop-Os.o loop-Oz.o
```

GCC also supports `-Os`, but its pipeline and codegen are not identical to Clang's. MSVC's `/O1` is a different product — do not equate flag names across vendors.

| Stage | What to investigate |

| Object generation | Emitted sections and machine code |

- [x] Object-file and final executable sizes
- [x] Generated IR, assembly, and CompilerSutraPerf artifacts under [`/files/clang-flags/-Os/`](/files/clang-flags/-Os/)

If you change the compiler version, CPU, source, or build settings, treat the result as a **new** experiment.

## Final takeaway

`-Os` is a size-oriented optimization choice, not a guarantee of smaller or faster code.

On this measured buffer kernel, `-Os` produced clearly smaller object code and clearly slower runtime than `-O2`, because Clang kept a scalar loop while `-O2` vectorized. `-Oz` made the kernel object slightly smaller still, but the linked executable grew — and runtime got worse again.

Inspect LLVM IR and machine code to see what changed. Use CompilerSutraPerf's `compiler_diff_batch.py` workflow to measure runtime and available counters. Measure size with `size` / `stat` separately. Publish the machine, compiler, commands, and artifacts with the numbers.

That is the difference between describing a compiler flag and evaluating its actual behavior.
