## At a glance

| Aspect | Behavior |
| :--- | :--- |
| **Primary purpose** | Emits global variables and constants into unique sections rather than shared aggregate sections (`.data`, `.bss`, `.rodata`). |
| **Optimization levels (`-O*`)** | Default is **off** (`-fno-data-sections`) across all standard `-O0`, `-O2`, `-O3`, `-Os`, `-Oz` levels on ELF/Mach-O host platforms, unless specified by target defaults or specified explicitly. |
| **Linker interaction** | Essential for dead-data elimination when paired with linker garbage collection (`-Wl,--gc-sections` for lld/bfd or `-Wl,-dead_strip` for ld64). |
| **Trade-off** | Increases object file header overhead and section table size; can marginally slow down link times if overused on broad codebases without dead code. |

## What this flag actually does

By default, Clang groups global variables into continuous shared sections based on initialization status and mutability:
- Initialized non-zero global data $\rightarrow$ `.data`
- Zero-initialized global data $\rightarrow$ `.bss`
- Read-only data / constants $\rightarrow$ `.rodata`

When `-fdata-sections` is enabled, the LLVM backend (`TargetLoweringObjectFile` / `AsmPrinter`) derives a dedicated section name for each global variable using its symbol name:
- `int static_var = 1;` $\rightarrow$ `.data.static_var`
- `int zero_var = 0;` $\rightarrow$ `.bss.zero_var`
- `const int const_var = 42;` $\rightarrow$ `.rodata.const_var`

This isolation removes implicit grouping dependencies inside compiled object files (`.o`). During the linking stage, an ELF linker configured with `--gc-sections` constructs a symbol reference graph starting from entry points (e.g., `_start` or `main`). Sections containing unreferenced global data symbols are omitted from the final binary execution image.

### Optimization Level Interactions

Standard optimization levels (`-O0` through `-Oz`) do not implicitly toggle `-fdata-sections`. The frontend passes `-fdata-sections` to `-cc1` as `CodeGenOpts.DataSections = 1`, which directly sets LLVM target machine configuration flags.

## Code example & assembly comparison

Consider a module containing an exported active global variable and an unused internal static variable:

<SourceCode
  language="cpp"
  title="data_sections_demo.c"
  code={`int used_global = 100;
static int unused_global = 200;

int get_val(void) {
    return used_global;
}`}
/>

When compiled without `-fdata-sections`, both globals are co-located in the default `.data` section. With `-fdata-sections`, separate section header declarations are emitted in assembly:

<AsmDiff
  beforeTitle="Default (-fno-data-sections)"
  beforeCode={`.text
.globl get_val
get_val:
    movl used_global(%rip), %eax
    ret

.data
.globl used_global
used_global:
    .long 100

unused_global:
    .long 200`}
  afterTitle="Explicit (-fdata-sections)"
  afterCode={`.text
.globl get_val
get_val:
    movl used_global(%rip), %eax
    ret

.section .data.used_global,"aw",@progbits
.globl used_global
used_global:
    .long 100

.section .data.unused_global,"aw",@progbits
unused_global:
    .long 200`}
/>

Notice that `.section .data.used_global` and `.section .data.unused_global` isolate each symbol. If `unused_global` has internal linkage and is never referenced in code, the linker's `--gc-sections` phase drops `.data.unused_global` entirely.

## How it works inside Clang

### 1. Driver Option Parsing
The Clang driver receives `-fdata-sections` (or `-fno-data-sections`) in `clang/lib/Driver/ToolChains/Clang.cpp`. The driver translates the command-line flag into a CC1 argument `-fdata-sections`.

* **Source reference**: [clang/lib/Driver/ToolChains/Clang.cpp#L5085-L5100](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.0/clang/lib/Driver/ToolChains/Clang.cpp#L5085-L5100)

### 2. Frontend CodeGenOptions Initialization
During CC1 invocation, `CompilerInvocation.cpp` parses `-fdata-sections` into `CodeGenOpts.DataSections`.

* **Source reference**: [clang/lib/Frontend/CompilerInvocation.cpp#L1620-L1635](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.0/clang/lib/Frontend/CompilerInvocation.cpp#L1620-L1635)

### 3. Backend TargetMachine Setup
When the LLVM backend initializes `TargetMachine` options inside `clang/lib/CodeGen/BackendUtil.cpp`, `CodeGenOpts.DataSections` is mapped to `llvm::TargetOptions::DataSections`.

* **Source reference**: [clang/lib/CodeGen/BackendUtil.cpp#L480-L490](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.0/clang/lib/CodeGen/BackendUtil.cpp#L480-L490)

### 4. CodeGen Section Selection (`TargetLoweringObjectFile`)
During assembly generation, LLVM's `AsmPrinter` queries `TargetLoweringObjectFileELF::SelectSectionForGlobal` (or target-specific variants) to select the destination section. When `TM.getDataSections()` is true, the section generator appends the symbol name to the standard section prefix (e.g., `.data.` + `SymbolName`).

* **Source reference**: [llvm/lib/Target/TargetLoweringObjectFile.cpp#L340-L360](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.0/llvm/lib/Target/TargetLoweringObjectFile.cpp#L340-L360)

## Related LLVM Optimizations & Backend Mechanisms

Classification: **backend/codegen**

| Mechanism | Relationship Label | Description |
| :--- | :--- | :--- |
| `TargetOptions::DataSections` | Directly controlled | Boolean backend option queried by target section emission routines. |
| `TargetLoweringObjectFileELF` | Backend mechanism | Formulates target ELF section names based on symbol attributes and driver settings. |
| `AsmPrinter` | Backend mechanism | Emits object file section headers based on selected section descriptors. |
| `-Wl,--gc-sections` | Related mechanism | Linker-level optimization pass that scans section graph roots to strip unreachable sections. |

### How to verify backend section assignment

You can inspect the LLVM TargetMachine selection directly by asking Clang to emit assembly without running the linker:

```bash
clang -O2 -fdata-sections -S data_demo.c -o - | grep '\.section'
```

Look for explicit section names such as `.section .rodata.str1.1` or `.section .bss.global_buffer`.
