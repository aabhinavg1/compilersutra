## What this flag actually does

-std= selects a language mode such as c17, c23, c++17, c++20, gnu17, or gnu++20. The frontend uses that mode for parsing, feature availability, predefined macros, and semantic rules; it is not a linker option and must be consistent across compatible translation units.

## Why use it / when not to use it

Use it when the language mode behavior matches the build contract. Do not enable it selectively across mutually dependent translation units when it changes preprocessing, language rules, ABI expectations, or runtime instrumentation. Verify the effect with the exact compiler and target used by CI.

:::caution
This option does not repair invalid source, undefined behavior, data races, or an inconsistent build contract. It only changes the compiler mechanism described above.
:::

## Performance impact

This option is not a runtime optimizer. It does not change generated code by itself the way `-O2` or `-fvectorize` does. If a macro, include path, language mode, or warning set changes which code you build, measure **that program** with [CompilerSutraPerf](/docs/project/compilersutra-perf/) (`csperf run` / `csperf diff`) the same as any other code change. Do not treat frontend flags as free speedups.

## Usage example

~~~bash
clang++ -std=c++20 -Wall -c main.cpp -o main.o
clang++ -std= -### -c main.cpp
~~~

## Adjacent options

Use the inverse or sibling spelling where available, and inspect the generated driver command with -###. Related controls include -O levels, -g, -I/-isystem, -D/-U, -fsanitize-recover, and target or linker options as appropriate.

## How it works inside Clang

### Implementation

| Stage | Source and implementation | What happens |
| --- | --- | --- |
| Options.td | [Options.td](https://github.com/llvm/llvm-project/blob/main/clang/include/clang/Options/Options.td) | Declares the joined language-standard option and the accepted language-mode spellings. |
| Driver parsing | [Clang.cpp](https://github.com/llvm/llvm-project/blob/main/clang/lib/Driver/ToolChains/Clang.cpp) | The driver validates the language option and forwards the effective mode to `cc1`; it also selects language-specific defaults. |
| Invocation setup | [CompilerInvocation.cpp](https://github.com/llvm/llvm-project/blob/main/clang/lib/Frontend/CompilerInvocation.cpp) | Language option parsing sets `LangOptions`, including standard version, GNU extensions, and feature toggles. |
| Frontend / AST | [LangOptions](https://github.com/llvm/llvm-project/blob/main/clang/include/clang/Basic/LangOptions.def) | Parser, Sema, and AST construction consult `LangOptions` to accept syntax and apply language semantics. |
| LLVM IR / codegen | [CodeGenModule](https://github.com/llvm/llvm-project/blob/main/clang/lib/CodeGen/CodeGenModule.cpp) | The selected language mode affects declarations, builtins, ABI-relevant attributes, and generated IR; LLVM does not parse `-std=`. |
| Linker | [Clang stage selection](https://clang.llvm.org/docs/CommandGuide/clang.html#stage-selection-options) | The linker sees objects and libraries, not the source language standard. |

~~~mermaid
flowchart LR
 A["-std="] --> B["Options.td"] --> C["Clang driver"] --> D["CompilerInvocation"] --> E["frontend / CodeGenOptions"] --> F["LLVM IR or diagnostics"] --> G["backend / linker"]
~~~

The -std= spelling is handled by the driver and translated into frontend, diagnostic, target, IR, or runtime state as shown above. LLVM and the linker consume the resulting representation; they do not generally parse the original user-facing spelling.
