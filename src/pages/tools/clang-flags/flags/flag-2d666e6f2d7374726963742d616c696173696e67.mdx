## At a glance

| | |
| --- | --- |
| **Architecture** | Target-independent; effect is most visible at `-O1` and above |
| **Category** | Language semantics / optimization |
| **Compiler** | Clang, including the C and C++ drivers |
| **Optimization** | Relaxes type-based alias analysis (TBAA) |
| **Risk** | Usually slower; can hide violations of the language aliasing rules |

:::note One-line summary
  Tell Clang not to use incompatible pointer types as proof that two memory accesses cannot refer to the same object.
:::

## What this flag actually does

- At optimization levels where strict aliasing is enabled.
- Clang may use the C and C++ aliasing rules to attach type-based alias information to `loads` and `stores`. Normally, Clang assumes that accesses through `int*` and `float*` do not normally refer to the same object. <br/>
- With `-fno-strict-aliasing`, Clang must conservatively assume they may alias.
- This is not a sanitizer and it does not make type-punning defined.
- It changes which transformations are permitted when the optimizer cannot otherwise prove that pointers overlap.
- The flag is the negative form of `-fstrict-aliasing` and is commonly selected by `-O0`, while optimization levels such as
   `-O2` enable strict aliasing unless overridden.

:::caution This does not repair undefined behavior

If a program accesses an object through an incompatible lvalue type, the C or C++ language rules may still make that access undefined. The flag reduces optimizer assumptions; it is not a portability guarantee for type punning.

:::

## Minimal example

The second store uses a `float *`, while the return reload uses an `int *`. With strict aliasing, Clang can conclude that the store cannot change `*ip`; with the flag, it must retain the reload.

## Why use it?
:::caution
Use it in these situations:

- **Legacy C or C++ code:** different pointer types may refer to the same memory in practice.
- **Compiler-specific code:** imported code may rely on aliasing behavior from another compiler.
- **Debugging optimizer changes:** compile both ways. If the output or behavior changes, an aliasing assumption may be involved.
- **Baseline comparisons:** use it to see what the compiler does when it must assume that pointers can overlap.
:::

:::important
Avoid using it as a general fix for a miscompiled program:

- Find and correct the invalid or ambiguous memory access first.
- Correctly typed code usually gets no benefit from this flag.
- The compiler may generate slower code because it cannot remove as many loads and stores.
- It may also lose some vectorization and other optimizations.
:::
## Performance impact

The flag has no useful universal speedup: it removes information from the optimizer. The cost depends on how many memory operations could otherwise be proven independent. Small functions may show no difference; pointer-heavy loops can retain reloads, lose vectorization, or execute more conservatively.

Runtime data was collected with [CompilerSutraPerf 0.1.2](/docs/project/compilersutra-perf/releases/0.1.2/) ([PyPI](https://pypi.org/project/compilersutra-perf/)). The workload processes separate `int` and `float` arrays for 100 repetitions, using Ubuntu Clang 18.1.3 on an AMD Ryzen 7 9700X under Linux. Each build used 3 warmup runs and 7 measured CPU trials; perf counters were disabled.

The exact testcase used for validation and timing was:

```c
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

__attribute__((noinline)) int64_t alias_work(int *ip, float *fp, size_t n) {
  int64_t sum = 0;
  for (size_t i = 0; i < n; ++i) {
    ip[i] += 1;
    fp[i] += 2.0f;
    sum += ip[i];
  }
  return sum + (int64_t)fp[n - 1];
}

int main(void) {
  const size_t n = 1u << 20;
  int *ip = (int *)malloc(n * sizeof(*ip));
  float *fp = (float *)malloc(n * sizeof(*fp));
  if (!ip || !fp) return 2;
  for (size_t i = 0; i < n; ++i) { ip[i] = (int)i; fp[i] = (float)i; }
  int64_t result = 0;
  for (int r = 0; r < 100; ++r) result += alias_work(ip, fp, n);
  printf("%lld\n", (long long)result);
  free(ip); free(fp);
  return 0;
}
```

## Compatibility

| Compiler / target | `-fno-strict-aliasing` |
| --- | --- |
| Clang, C / C++ | Yes |
| Clang, other target triples | Yes; the alias analysis is target-independent |
| GCC, C / C++ | Yes |
| MSVC | No equivalent flag with the same spelling or contract |

The flag must be applied consistently when one translation unit’s optimization depends on aliasing across an API boundary. It does not alter the object representation or calling convention, so separately compiled objects can link; it can still expose inconsistent assumptions when code is inlined or optimized under different language contracts.

## Usage example

Apply it to the compilation commands that need conservative alias analysis:

```python
clang -O2 -fno-strict-aliasing -c legacy.c -o legacy.o
clang++ -O2 -fno-strict-aliasing -c legacy.cpp -o legacy.o
```

To inspect the frontend option that the driver passes to `cc1`:

```python
clang -O2 -fno-strict-aliasing -### -c legacy.c
# look for: -relaxed-aliasing
```
:::tip
The `-###` output from Clang 18.1.3 contains `-relaxed-aliasing`; this is the internal spelling, not a replacement command-line interface.
:::

## Adjacent options

- `-fstrict-aliasing` — enable the type-based aliasing assumptions; this is the inverse.
- `-O2` / `-O3` — optimization levels that normally enable strict aliasing unless overridden.
- `-fno-vectorize` — a separate, narrower way to disable loop vectorization; it does not change aliasing semantics.
- `-fno-strict-overflow` — similarly relaxes a different optimizer contract, this time around signed-integer overflow.
- `-fsanitize=undefined` — diagnoses some undefined behavior, but it is not an alias-analysis mode switch and does not replace this flag.

## How it works inside Clang

The flag is handled in four layers: the public option table, driver forwarding, frontend invocation state, and TBAA metadata generation. It is not a target-specific `TargetInfo` switch; the effect is target-independent and appears in the LLVM IR produced by Clang.

### Implementation

| Stage | Source and implementation | What happens |
| --- | --- | --- |
| **Options.td** | [`clang/include/clang/Options/Options.td:4012-4014`](https://github.com/llvm/llvm-project/blob/main/clang/include/clang/Options/Options.td#L4012-L4014), [`:4591-4593`](https://github.com/llvm/llvm-project/blob/main/clang/include/clang/Options/Options.td#L4591-L4593), [`:8130-8132`](https://github.com/llvm/llvm-project/blob/main/clang/include/clang/Options/Options.td#L8130-L8132) | Declares `-fno-strict-aliasing`, `-fstrict-aliasing`, and the internal `-relaxed-aliasing` `cc1` option. TableGen emits the option database and the marshalling code. |
| **Driver parsing** | [`clang/lib/Driver/ToolChains/Clang.cpp:6115-6124`](https://github.com/llvm/llvm-project/blob/main/clang/lib/Driver/ToolChains/Clang.cpp#L6115-L6124) | `Args.hasFlag(...)` resolves the last strict/negative spelling and forwards `-relaxed-aliasing` to `cc1` when strict aliasing is disabled. |
| **Invocation setup** | [`clang/lib/Frontend/CompilerInvocation.cpp:3774-3780`](https://github.com/llvm/llvm-project/blob/main/clang/lib/Frontend/CompilerInvocation.cpp#L3774-L3780) | The generated marshalling block parses the `cc1` option into `CodeGenOpts.RelaxedAliasing`. The field is generated from the `MarshallingInfoFlag<CodeGenOpts<...>>` record in `Options.td`, rather than hand-written in `CompilerInvocation.cpp`. |
| **Code generation** | [`clang/lib/CodeGen/CodeGenTBAA.cpp:505-514`](https://github.com/llvm/llvm-project/blob/main/clang/lib/CodeGen/CodeGenTBAA.cpp#L505-L514) | `CodeGenTBAA::getTBAAStructInfo()` checks `CodeGenOpts.RelaxedAliasing` and avoids constructing strict struct-path TBAA information when the flag is enabled. |
| **LLVM backend** | [LLVM TBAA metadata reference](https://llvm.org/docs/LangRef.html#type-based-alias-analysis-metadata) | LLVM optimization passes consume the reduced alias metadata. The target backend then lowers the resulting IR; it does not parse `-fno-strict-aliasing` itself. |

The public option is therefore translated by the driver rather than `passed directly to LLVM`.

> `clang -###` exposes the boundary:

```python
clang -O2 -fno-strict-aliasing -### -c alias.c
# inspect the printed cc1 command for: -relaxed-aliasing
```

To inspect the generated IR and compare the frontend result with strict aliasing enabled:

```python
clang -O2 -fno-strict-aliasing -S -emit-llvm alias.c -o alias-relaxed.ll
clang -O2 -fstrict-aliasing -S -emit-llvm alias.c -o alias-strict.ll
```

The important implementation detail is that the flag does not make incompatible type-punning defined. It changes the TBAA facts attached during Clang code generation, which limits the alias-based transformations available to LLVM. `TargetInfo`, instruction selection, object emission, and linking proceed normally after that IR-level decision.

## Related LLVM Optimizations & Backend Mechanisms

**Flag category:** LLVM IR optimization / analysis (TBAA). Affects alias analysis, not a single named “aliasing pass”.

| Mechanism | Stage | Relationship | Effect |
| :--- | :--- | :--- | :--- |
| TBAA metadata emission | Clang CodeGen | Directly controlled | Disabling strict aliasing suppresses / weakens TBAA metadata |
| Alias analysis consumers (GVN, LICM, vectorize, …) | LLVM IR | Indirectly affected | Fewer type-based no-alias facts → more conservative transforms |
| Language UB rules for type-based aliasing | Frontend semantics | Related mechanism | Flag does not “fix” UB; it changes optimizer assumptions |

### How to verify

```bash
clang -O2 -S -emit-llvm w.c -o strict.ll
clang -O2 -fno-strict-aliasing -S -emit-llvm w.c -o nostrict.ll
rg 'TBA|!tbaa' strict.ll nostrict.ll
```
