## At a glance

| | |
| --- | --- |
| **Architecture** | Primarily ELF targets (Linux, BSD); behavior varies by triple |
| **Category** | Code generation / linking model |
| **Compiler** | Clang driver (also Flang); GCC has the same spelling |
| **Effect** | Access globals and extern symbols through GOT / PC-relative sequences |
| **Risk** | Tiny runtime cost vs absolute addressing; wrong model breaks shared-library linking |

**One-line summary:** compile so the resulting `.o` can be linked into a shared library and relocated when loaded at an arbitrary base address.

## What this flag actually does

`-fpic` asks Clang to emit **position-independent code** using the **small PIC** model on ELF x86_64. Instead of baking in absolute addresses for globals and external symbols, the compiler generates instructions that locate data through the **Global Offset Table (GOT)** or PC-relative fixups that the dynamic linker can adjust at load time.

That matters because a shared library (`.so`) can be mapped at **different virtual addresses** in different processes (ASLR) and even move between runs. Code compiled without PIC often contains absolute relocations that cannot be dropped into a shared object.

<Callout tone="info" title="Not the same as -fPIE">
  **`-fpic`** → position-independent code for **shared objects** (`.so`). You typically pair compiled objects with `-shared` when linking the library.
  **`-fPIE`** → position-independent code for **executables**; link with **`-pie`** to get a PIE binary. Both enable ASLR-friendly output, but the link step differs.
</Callout>

A function that touches a global variable is enough to see the codegen change:

### Before vs. after assembly

Both builds use `clang -O2 -S` on x86_64 Linux. Changed lines are highlighted.

<AsmDiff
  beforeTitle="Without -fpic (direct addressing)"
  afterTitle="With -fpic (GOT indirection)"
  before={`\
bump:
\tmovl\tcounter(%rip), %eax
\tincl\t%eax
\tmovl\t%eax, counter(%rip)
\tretq`}
  after={`\
bump:
\tmovq\tcounter@GOTPCREL(%rip), %rcx
\tmovl\t(%rcx), %eax
\tincl\t%eax
\tmovl\t%eax, (%rcx)
\tretq`}
  note="Clang 18, x86_64-pc-linux-gnu, -O2. -fpic adds a GOT lookup (movq counter@GOTPCREL) and accesses memory through %rcx. Extra instruction and one memory indirection vs direct counter(%rip)."
/>

**What changed:** the non-PIC build uses `%rip`-relative addressing straight to `counter`. The PIC build loads a GOT slot first, then reads/writes through that pointer — relocatable at load time.

## `-fpic` vs `-fPIC` vs `-fPIE`

| Flag | Typical output | Link with | Use case |
| --- | --- | --- | --- |
| **`-fpic`** | Small PIC | `-shared` | Shared libraries on x86_64 (default choice) |
| **`-fPIC`** | Large / fully PIC | `-shared` | When small PIC limits are hit (some archs / huge data) |
| **`-fPIE`** | PIC for executables | **`-pie`** | Hardened binaries, ASLR for main program |
| **`-fno-pic`** | Absolute / non-PIC | (static or fixed base) | Kernel code, firmware, or when you know the load address |

On **x86_64 Linux**, `-fpic` and `-fPIC` often produce similar code for simple examples; the distinction matters more on architectures with stricter PIC models.

## Why would anyone use this?

- **Building shared libraries** (`.so`): `-fpic -shared` is the standard recipe on Linux.
- **ASLR / security hardening**: PIC lets the loader place mappings at random bases without relinking.
- **Plugins and dlopen**: code loaded at runtime must not assume fixed addresses.
- **Distributable SDKs**: one `.so` binary works across processes regardless of load address.

<Callout tone="warning" title="Build the whole DSO with PIC">
  Every object linked into a shared library should be compiled with `-fpic` (or `-fPIC`). Mixing PIC and non-PIC objects into one `.so` fails at link time or produces subtle relocation errors.
</Callout>

## Performance impact

PIC is usually a **small** cost — but the cost shows up in **instructions first**, not always in wall time.

**Mechanism (from the assembly above):**

- **Extra instructions** for GOT setup on global accesses (`movq counter@GOTPCREL` + load through pointer).
- **One extra memory indirection** vs direct `%rip` addressing.
- **Not an optimization-level change** — combine freely with `-O2`, `-O3`, LTO, etc.

## When to use it

- Compiling **object files** that will be linked into a **shared library**.
- Any translation unit that ends up in a `.so`, including static archives (`.a`) later linked into a shared object.
- Security-sensitive Linux packages that ship shared modules loaded by `dlopen`.

## When not to use it

- **Single static executable** with no PIC requirement — many distros default to `-fPIE` for executables instead; use the right model for the link step.
- **Freestanding / kernel** code with a fixed link address — often `-fno-pic` or platform-specific flags.
- **Mixing models** in one shared library — keep PIC consistent across all objects.

## Typical usage

**Shared library (two-step):**

```bash
clang -fpic -O2 -c libfoo.c -o libfoo.o
clang -shared -o libfoo.so libfoo.o
```

**See what the driver passes:**

```bash
clang -fpic -O2 -### -c libfoo.c
```

**Contrast with PIE executable:**

```bash
clang -fPIE -O2 -c main.c -o main.o
clang -pie -o app main.o
```

Negate with **`-fno-pic`** when you need to force non-PIC code generation (platform-dependent defaults apply).

## How it works inside Clang

The driver option is declared in `clang/include/clang/Driver/Options.td` (around line 6507) as part of the target-independent `f_Group` code-generation flags. When `-fpic` is present, the driver sets the relocation / code-model state passed to `clang -cc1` and the backend so that:

1. Global and external variable references emit **GOT-relative** or PC-relative relocations.
2. The object file contains relocation entries the **static or dynamic linker** can apply when the segment is mapped.
3. Text remains valid regardless of the final load bias.

Inspect the chosen model with:

```bash
clang -fpic -O2 -### -c file.c 2>&1 | rg 'pic|relocation|code-model'
```

## Compatibility

| Compiler / context | `-fpic` |
| --- | --- |
| Clang / Flang on Linux x86_64 | Yes — standard for `.so` |
| GCC | Same spelling, same general meaning |
| MSVC Windows | Different mechanism (`/MD`, DLL import libs) |
| macOS | Often `-fPIC` for dylibs; check platform docs |

## Adjacent options

- **`-fPIC`** — large PIC model when small PIC is insufficient.
- **`-fPIE` / `-pie`** — PIC for executables, not shared libraries.
- **`-fno-pic`** — disable PIC code generation.
- **`-shared`** — linker flag to produce a shared object (used after `-fpic` compile).
- **`-fvisibility=hidden`** — often combined with shared libraries to trim exported symbols.

## Related LLVM Optimizations & Backend Mechanisms

**Flag category:** Code generation / relocation model. **No direct IR optimization pass.**

| Mechanism | Stage | Relationship | Effect |
| :--- | :--- | :--- | :--- |
| Relocation model (PIC) | Driver → TargetMachine | Directly controlled | Emits position-independent code sequences |
| GOT/PC-relative addressing | Machine backend | Backend mechanism | Indirect data/code refs via GOT/PLT as needed |
| IR dso_local / local_unnamed_addr etc. | LLVM IR | Indirectly affected | Visibility/locality attributes may change |

### How to verify

```bash
clang -O2 -fpic -S w.c -o pic.s
clang -O2 -fno-pic -S w.c -o nopic.s   # where supported
clang -### -fpic -c w.c 2>&1 | rg -i 'pic|relocation'
```
