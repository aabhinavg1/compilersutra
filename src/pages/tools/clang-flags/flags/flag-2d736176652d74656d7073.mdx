
## What this flag actually does

`-save-temps` instructs the Clang driver to retain intermediate artifacts created during compilation instead of streaming them through pipes or placing them in deleted temporary files.

When compiling C or C++ source code, the compilation pipeline typically performs multiple distinct steps:
1. **Preprocessing** (`.cpp` $\rightarrow$ `.ii` or `.c` $\rightarrow$ `.i`)
2. **Compilation / Frontend Parsing & CodeGen** (`.ii` $\rightarrow$ `.bc` or `.s`)
3. **Backend / Assembly** (`.s` $\rightarrow$ `.o`)
4. **Linking** (`.o` $\rightarrow$ executable / shared library)

By default, Clang combines these steps in memory or passes temporary filenames between subprocesses, cleaning them up upon completion. Passing `-save-temps` forces the driver to write each intermediate stage to the current working directory using filenames based on the input source file.

<Callout type="info" title="Defaults across optimization levels">
**O-level sensitivity:** Optimization levels (`-O0`, `-O1`, `-O2`, `-O3`, `-Os`, `-Oz`, `-Ofast`) do not alter the behavior of `-save-temps`. The flag governs driver pipeline artifact handling rather than frontend or backend lowering.
</Callout>

### Differences from `-save-temps=obj`

* `-save-temps` (and `-save-temps=cwd`): Writes intermediate output files (`.i`, `.s`, `.bc`) into the current working directory.
* `-save-temps=obj`: Writes intermediate output files into the directory specified by the output flag (`-o`).

## How it works inside Clang

`-save-temps` is evaluated early in driver construction. It influences how the driver constructs jobs (`clang::driver::Compilation` and `clang::driver::Job`) and determines whether temporary paths or permanent on-disk filenames are generated.

### 1. Driver Option Parsing

The flag is defined as an alias in the driver option table:

* [`clang/include/clang/Driver/Options.td`](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.0/clang/include/clang/Driver/Options.td#L5325-L5327)

```tablegen
def save_temps : Flag<["-"], "save-temps">, Flags<[NoXarchOption]>,
  HelpText<"Save intermediate compilation results">,
  Alias<save_temps_EQ>, AliasArgs<["cwd"]>;
```

When `-save-temps` is supplied on the command line, the driver translates it into `-save-temps=cwd`.

### 2. Pipeline Action Generation and Filename Resolution

During job graph construction, `Driver::BuildJobsForAction` evaluates whether saved temps are enabled via `SaveTempsMode`:

* [`clang/lib/Driver/Driver.cpp`](https://github.com/llvm/llvm-project/blob/llvmorg-19.1.0/clang/lib/Driver/Driver.cpp#L5710-L5750)

When `SaveTempsMode` is set, the driver bypasses creation of randomized temporary paths (`/tmp/main-XXXXXX.s`) and instead assigns deterministic filenames (e.g., `main.i`, `main.s`) directly in the targeted directory.

Because `-save-temps` forces separate pipeline stages to communicate via file on disk rather than unified in-process memory structures, passing `-save-temps` also causes Clang to invoke separate sub-tools or `-cc1` stages explicitly.

## Related LLVM Optimizations & Backend Mechanisms

### Category: Diagnostic / Frontend / Driver Policy

`-save-temps` operates purely at the driver pipeline level. It does not map to an LLVM IR pass, IR attribute, or machine-specific code generation pass.

| Mechanism / Pass Name | Relationship Label | Description |
| :--- | :--- | :--- |
| **Driver Job Graph Construction** | Directly controlled | Dictates whether intermediate steps write to standard temporary locations or retain deterministic on-disk files. |
| **`-emit-llvm` / `-S`** | Related mechanism | Manual sub-flags used to emit specific IR or assembly stages individually without saving all pipeline stages. |

### Source Investigation & Verification

To observe how `-save-temps` alters driver execution without executing the compiler, run with `-###`:

```bash
clang++ -save-temps -O2 -c main.cpp -o main.o -###
```

**Verified driver invocation output:**
The driver output confirms that `-cc1` is invoked with explicit output filenames for preprocessed source (`main.ii`) and backend output (`main.s`), preserving every intermediate artifact on disk.
