## What this flag actually does

-pthread is a driver option whose exact effects are target and runtime dependent. On Unix-like targets it commonly enables thread-related compile definitions and link inputs; it does not make unsynchronized accesses data-race-free and does not replace the C++ memory model.

## Minimal realistic example

<SourceCode file="example.cpp" flag="-pthread" language="c++" code={String.raw`#include <thread>

void work() {}

int main() {
  std::thread worker(work);
  worker.join();
}`} note="This complete program starts one thread and waits for it. Compile and link it with -pthread so the platform thread configuration is applied consistently." />

## Before vs. after driver command

Ubuntu Clang 18.1.3, target x86_64-pc-linux-gnu. For -pthread, the important observable difference is the driver’s forwarded compile and link arguments, not a guaranteed change to a small function’s assembly.

~~~text
$ clang++ -### -pthread -c example.cpp
... -pthread ...

$ clang++ -### -pthread example.cpp -o app
... -pthread ...
... -lpthread ...
~~~

On this Linux toolchain, -pthread reaches cc1 and adds -lpthread to the final link command. The exact runtime-library spelling is platform-dependent.

## Why use it / when not to use it

Use it when the threading / driver behavior matches the build contract. Do not enable it selectively across mutually dependent translation units when it changes preprocessing, language rules, ABI expectations, or runtime instrumentation. Verify the effect with the exact compiler and target used by CI.

:::caution
This option does not repair invalid source, undefined behavior, data races, or an inconsistent build contract. It only changes the compiler mechanism described above.
:::

## Adjacent options

Use the inverse or sibling spelling where available, and inspect the generated driver command with -###. Related controls include -O levels, -g, -I/-isystem, -D/-U, -fsanitize-recover, and target or linker options as appropriate.

## How it works inside Clang

### Implementation

| Stage | Source and implementation | What happens |
| --- | --- | --- |
| Options.td | [Options.td](https://github.com/llvm/llvm-project/blob/main/clang/include/clang/Options/Options.td) | Declares the thread-model driver option and its inverse where the target supports it. |
| Driver parsing | [Clang.cpp](https://github.com/llvm/llvm-project/blob/main/clang/lib/Driver/ToolChains/Clang.cpp) | The driver records the requested thread model and passes target/runtime-specific compile and link arguments. |
| Invocation setup | [CompilerInvocation.cpp](https://github.com/llvm/llvm-project/blob/main/clang/lib/Frontend/CompilerInvocation.cpp) | The effective thread model is stored in target and language invocation state where applicable. |
| Frontend / codegen | [TargetOptions](https://github.com/llvm/llvm-project/blob/main/clang/include/clang/Basic/TargetOptions.h) | Target-specific predefined macros, TLS lowering, and thread-related code-generation decisions consult the selected platform model. |
| LLVM / backend | [LLVM target infrastructure](https://github.com/llvm/llvm-project/tree/main/llvm/lib/Target) | LLVM lowers the resulting target state; it does not parse the portable driver spelling `-pthread`. |
| Linker | [Clang.cpp](https://github.com/llvm/llvm-project/blob/main/clang/lib/Driver/ToolChains/Clang.cpp) | The driver adds platform-specific thread runtime/library behavior to the link command where required. |

~~~mermaid
flowchart LR
 A["-pthread"] --> B["Options.td"] --> C["Clang driver"] --> D["CompilerInvocation"] --> E["frontend / CodeGenOptions"] --> F["LLVM IR or diagnostics"] --> G["backend / linker"]
~~~

The -pthread spelling is handled by the driver and translated into frontend, diagnostic, target, IR, or runtime state as shown above. LLVM and the linker consume the resulting representation; they do not generally parse the original user-facing spelling.
